## The Theory (The What)

**Runtime** (or "execution time") is the phase when compiled code is actually running on a device or virtual machine. On Android, this means execution within the Android Runtime (ART), which replaced Dalvik since Android 5.0. At runtime, the system handles memory allocation, [garbage collection]({{ "/en/glossary/garbage-collector/" | relative_url }}), thread scheduling, virtual method dispatch ([polymorphism]({{ "/en/glossary/polymorphism/" | relative_url }})), and exception handling. Runtime errors — `NullPointerException`, `ClassCastException`, `OutOfMemoryError` — are the most expensive errors because they affect real users.

## The Senior Nuance

- Kotlin's type system is designed to shift errors from runtime to [compile time]({{ "/en/glossary/compile-time/" | relative_url }}): null safety eliminates `NullPointerException`, smart casts eliminate `ClassCastException`, and sealed `when` exhaustiveness eliminates unhandled state branches.
- **Type erasure**: Generic type parameters (`T` in `List<T>`) are not available at runtime on the JVM. This is why `is List<String>` doesn't compile — the runtime only sees `List`. Kotlin's `reified` keyword on `inline` functions is the escape hatch, as the compiler inlines the actual type at each call site.
- **ART optimizations**: Ahead-of-Time (AOT) compilation, profile-guided optimization (PGO), and JIT compilation all happen at or around runtime to improve performance. Understanding these helps explain why "first run" can be slower than subsequent runs.
- **Runtime reflection** (`::class`, `KClass`, `java.lang.reflect`) is powerful but expensive — it bypasses compile-time safety and has measurable performance overhead. Prefer compile-time alternatives (annotation processing, sealed hierarchies) whenever possible.
