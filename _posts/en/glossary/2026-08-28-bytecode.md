## The Theory (The What)

**Bytecode** is the intermediate, platform-independent representation that the Kotlin/Java compiler produces from [source code]({{ "/en/glossary/source-code/" | relative_url }}) at [compile time]({{ "/en/glossary/compile-time/" | relative_url }}). It is stored in `.class` files (or `.dex` files on Android) and executed by the [JVM]({{ "/en/glossary/jvm/" | relative_url }}) or ART (Android Runtime). Bytecode is not human-readable source nor native machine code — it sits between the two, enabling the "write once, run anywhere" promise of JVM-based languages.

## The Senior Nuance

- Kotlin source and JVM bytecode are not 1:1. Features like [extension functions]({{ "/en/glossary/extension-functions/" | relative_url }}), default parameters, data class-generated methods, and [inline functions]({{ "/en/glossary/inline-functions/" | relative_url }}) all produce bytecode that has no direct source-level equivalent. The IntelliJ "Show Kotlin Bytecode" → "Decompile" tool is essential for understanding what the compiler actually produces.
- On Android, `.class` bytecode is further compiled to `.dex` (Dalvik Executable) bytecode by D8/R8. R8 also performs optimizations and code shrinking — so the final bytecode running on-device may differ significantly from what `kotlinc` produced.
- **Compile-time constants** (`const val`) with [primitives]({{ "/en/glossary/primitives/" | relative_url }}) and `String` are inlined directly into the bytecode at every usage site — the constant's value is copied, not referenced. This eliminates any [runtime]({{ "/en/glossary/runtime/" | relative_url }}) field access.
- Generic type parameters are erased in bytecode (type erasure): `List<String>` and `List<Int>` produce identical bytecode (`List`). The [`reified`]({{ "/en/glossary/reified/" | relative_url }}) keyword on [inline functions]({{ "/en/glossary/inline-functions/" | relative_url }}) works around this by substituting the actual type at each call site during compilation.
