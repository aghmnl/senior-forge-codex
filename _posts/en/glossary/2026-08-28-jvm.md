## The Theory (The What)

The **JVM** (Java Virtual Machine) is the [runtime]({{ "/en/glossary/runtime/" | relative_url }}) environment that executes [bytecode]({{ "/en/glossary/bytecode/" | relative_url }}) compiled from [source code]({{ "/en/glossary/source-code/" | relative_url }}) written in Java, Kotlin, Scala, or other JVM languages. It provides memory management ([garbage collection]({{ "/en/glossary/garbage-collector/" | relative_url }})), thread scheduling, class loading, security sandboxing, and just-in-time (JIT) compilation. On Android, ART (Android Runtime) replaces the standard JVM but retains the same bytecode contract — code compiled for the JVM runs on ART after DEX conversion.

## The Senior Nuance

- The JVM is where **type erasure** happens: generic type parameters (`T` in `List<T>`) are removed from bytecode. The JVM has no knowledge of `List<String>` vs. `List<Int>` at runtime — it only sees `List`. This is why [`reified`]({{ "/en/glossary/reified/" | relative_url }}) requires [`inline` functions]({{ "/en/glossary/inline-functions/" | relative_url }}): the compiler inlines the actual type at each call site before the JVM ever sees it.
- Understanding JVM memory layout (heap, stack, metaspace) explains boxing costs: [primitives]({{ "/en/glossary/primitives/" | relative_url }}) live on the stack (cheap), boxed equivalents live on the heap (allocation + GC cost). Kotlin's type system maps `Int` → JVM `int` and `Int?` → `Integer` — the question mark is the boxing boundary.
- JVM's JIT compiler profiles running code and optimizes hot paths — method inlining, escape analysis, loop unrolling. On Android, ART uses a combination of AOT (at install time), JIT (at runtime), and profile-guided optimization (PGO) for similar results.
- **`@JvmStatic`**, **`@JvmField`**, **`@JvmOverloads`**, and **`@JvmName`** are Kotlin annotations that control how [compile time]({{ "/en/glossary/compile-time/" | relative_url }}) translates Kotlin constructs to JVM bytecode — they exist because Kotlin's object model doesn't map 1:1 to JVM's.

```kotlin
// From FollowApp Suite — LabelRepositoryImpl.kt
class LabelRepositoryImpl @Inject constructor(
    private val labelDao: LabelDao,
    private val presetDao: PresetDao
) : LabelRepository { ... }
```

`@Inject` tells the DI framework (Hilt/Dagger) which JVM constructor to use. The JVM loads this class, Hilt's generated code calls the constructor, and the JVM's garbage collector manages the instance's lifecycle.
