## The Theory (The What)

A **Map** in Kotlin is a collection of key-value pairs where each key is unique. The standard library provides `Map<K, V>` (read-only) and `MutableMap<K, V>` (modifiable). Common implementations include `HashMap`, `LinkedHashMap`, and `sortedMapOf`. Factory functions like `mapOf()` and `mutableMapOf()` create instances concisely.

```kotlin
// From FollowApp Suite — PresetMapper.kt
fun deserializeLabelFilters(json: String): Map<String, LabelFilterState> {
    if (json.isBlank() || json == "{}") return emptyMap()
    val obj = JSONObject(json)
    val result = mutableMapOf<String, LabelFilterState>()
    obj.keys().forEach { key ->
        runCatching { LabelFilterState.valueOf(obj.getString(key)) }
            .onSuccess { result[key] = it }
    }
    return result
}
```

## The Senior Nuance

- Kotlin separates the read-only `Map` interface from `MutableMap`. Returning `Map` from a function signals that callers should not [mutate]({{ "/en/glossary/mutation/" | relative_url }}) the collection — though the underlying instance may still be mutable. This is an intent signal, not a compile-time guarantee.
- When using a `data class` as a map key, only [primary constructor]({{ "/en/glossary/primary-constructor/" | relative_url }}) properties participate in `hashCode()` and `equals()`. If a body property changes between insertions, the map still finds the entry — but if a constructor property changes (via a mutable `var`), the entry becomes unreachable. Prefer immutable keys.
- `mapOf("a" to 1)` uses the `to` infix function, which creates a `Pair`. For large maps, `buildMap { put("a", 1) }` avoids intermediate `Pair` allocations.
