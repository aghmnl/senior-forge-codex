## The Theory (The What)

**`@Binds`** is a [Dagger]({{ "/en/glossary/dagger/" | relative_url }}) annotation used inside a [`@Module`]({{ "/en/glossary/module-annotation/" | relative_url }}) to declare that an interface should be satisfied by a specific implementation. Unlike `@Provides`, which requires a method body, `@Binds` is an `abstract` method — the [annotation processor]({{ "/en/glossary/annotation-processing/" | relative_url }}) generates the binding at [compile time]({{ "/en/glossary/compile-time/" | relative_url }}) without any runtime overhead.

```kotlin
// From FollowApp Suite — RepositoryModule.kt
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {

    @Binds
    abstract fun bindTaskRepository(
        taskRepositoryImpl: TaskRepositoryImpl
    ): TaskRepository

    @Binds
    abstract fun bindLabelRepository(
        labelRepositoryImpl: LabelRepositoryImpl
    ): LabelRepository
}
```

## The Senior Nuance

- **`@Binds` vs `@Provides`**: Use `@Binds` when mapping an interface to its implementation (no logic needed). Use `@Provides` when you need to call a constructor, configure a builder, or return a third-party type. `@Binds` generates more efficient code — [Dagger]({{ "/en/glossary/dagger/" | relative_url }}) can skip the factory class entirely.
- **Single parameter rule**: A `@Binds` method takes exactly one parameter (the implementation) and returns the interface type. The implementation must have an [`@Inject`]({{ "/en/glossary/inject/" | relative_url }}) constructor so Dagger knows how to create it.
- **Module must be abstract**: `@Binds` methods are `abstract`, so the module class must be `abstract class` (not `object`). This is why projects split modules: `abstract class RepositoryModule` for `@Binds`, `object DatabaseModule` for `@Provides`.
- **Scoping**: `@Binds` itself doesn't scope the binding. Add `@Singleton` or another scope annotation to cache the instance across the component's lifetime.
