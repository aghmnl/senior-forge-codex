## The Theory (The What)

A **hot loop** (high-frequency loop) is a loop that executes at a very high frequency or iterates over large collections in performance-critical paths. On Android, the canonical examples are `onDraw()` (called 60–120 times per second), `onMeasure()`/`onLayout()`, and [Jetpack Compose]({{ "/en/glossary/jetpack-compose/" | relative_url }}) recomposition lambdas. Any [allocation]({{ "/en/glossary/allocations/" | relative_url }}) inside a hot loop multiplies its cost by the iteration count, creating [Garbage Collector]({{ "/en/glossary/garbage-collector/" | relative_url }}) pressure that causes frame drops (jank).

```kotlin
// Not found in FAS — standalone example
// BAD: allocating inside onDraw — 60 objects/sec × 3 = 180 allocations/sec
override fun onDraw(canvas: Canvas) {
    val paint = Paint()                      // allocation every frame
    val rect = RectF(0f, 0f, width, height)  // allocation every frame
    canvas.drawRoundRect(rect, 12f, 12f, paint)
}

// GOOD: pre-allocate and reuse
private val paint = Paint()
private val rect = RectF()

override fun onDraw(canvas: Canvas) {
    rect.set(0f, 0f, width.toFloat(), height.toFloat())
    canvas.drawRoundRect(rect, 12f, 12f, paint)
}
```

## The Senior Nuance

- The 16ms frame budget (60 fps) or 8ms (120 fps) means every microsecond counts inside a hot loop. A single [autoboxing]({{ "/en/glossary/autoboxing/" | relative_url }}) in a loop of 1,000 iterations creates 1,000 `Integer` objects on the [heap]({{ "/en/glossary/heap/" | relative_url }}). Use [`IntArray`]({{ "/en/glossary/intarray/" | relative_url }}) and [primitive]({{ "/en/glossary/primitives/" | relative_url }}) types to avoid this.
- [Inline functions]({{ "/en/glossary/inline-functions/" | relative_url }}) are critical inside hot loops: a non-inline [lambda]({{ "/en/glossary/lambdas/" | relative_url }}) passed to a [higher-order function]({{ "/en/01-kotlin-core/higher-order-functions-lambdas/" | relative_url }}) allocates a wrapper object on each call. Kotlin's stdlib functions (`map`, `filter`, `forEach`) are all `inline`, so they don't allocate — but custom HOFs must be marked `inline` explicitly.
- In Compose, recomposition is the hot loop. Composable functions re-execute when their inputs change. Allocating inside a composable (creating new objects in the body instead of using `remember`) causes the same problems as allocating in `onDraw()`.
- Android Studio's Memory Profiler and Allocation Tracker visualize allocations over time. The "Allocations" flame chart shows exactly which methods are allocating in hot paths. Profile first — never optimize hot loops based on intuition alone.
- String concatenation (`"$a + $b"`) inside a hot loop allocates a new `StringBuilder` and `String` on each iteration. For repeated string building, reuse a `StringBuilder` declared outside the loop.
