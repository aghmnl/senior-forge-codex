## The Theory (The What)

**`@Inject`** is a JSR-330 standard annotation that marks a [constructor]({{ "/en/glossary/constructor/" | relative_url }}), field, or method as an injection point for a dependency injection framework. In [Dagger]({{ "/en/glossary/dagger/" | relative_url }})/[Hilt]({{ "/en/glossary/hilt/" | relative_url }}), `@Inject` on a constructor tells the [annotation processing]({{ "/en/glossary/annotation-processing/" | relative_url }}) pipeline how to create instances of that class — the processor generates a `Factory` class at [compile time]({{ "/en/glossary/compile-time/" | relative_url }}) that knows how to provide each parameter.

```kotlin
// From FollowApp Suite — LabelRepositoryImpl.kt
class LabelRepositoryImpl @Inject constructor(
    private val labelDao: LabelDao,
    private val labelOptionDao: LabelOptionDao
) : LabelRepository {
    // ...
}
```

## The Senior Nuance

- **Constructor injection is preferred**: `@Inject constructor(...)` is the idiomatic pattern in Android. It makes dependencies explicit, supports immutability (`val` parameters), and enables straightforward unit testing — just pass fakes to the constructor.
- **Field injection exists but is limited**: `@Inject lateinit var dep: SomeType` is used only where the framework controls instantiation (Activities, Fragments). It requires the field to be non-private and mutable — a compromise.
- **`@Inject` alone is not enough**: The class must either be bound in a [`@Module`]({{ "/en/glossary/module-annotation/" | relative_url }}) or live in a scope [Hilt]({{ "/en/glossary/hilt/" | relative_url }}) can see. `@Inject constructor` on an `internal` class in a different module won't be discovered without an explicit binding.
- **JSR-330 standard**: `@Inject` comes from `javax.inject`, not from [Dagger]({{ "/en/glossary/dagger/" | relative_url }}) itself. This means classes annotated with `@Inject` are not locked into Dagger — any JSR-330 compliant framework can provide them.
