## The Theory (The What)

**kapt** (Kotlin Annotation Processing Tool) is the original [annotation processing]({{ "/en/glossary/annotation-processing/" | relative_url }}) pipeline for Kotlin projects. It bridges Kotlin code to the Java `javax.annotation.processing` API by first generating Java [stubs]({{ "/en/glossary/stubs/" | relative_url }}) from Kotlin [source code]({{ "/en/glossary/source-code/" | relative_url }}), then running Java annotation processors against those stubs. kapt is being superseded by [KSP]({{ "/en/glossary/ksp/" | relative_url }}), which processes Kotlin symbols directly without stub generation.

## The Senior Nuance

- **Stub generation is the bottleneck**: kapt must generate a Java stub file for every Kotlin source file before any processor runs. This step alone can double [compile-time]({{ "/en/glossary/compile-time/" | relative_url }}) in large projects — it's the main reason teams migrate to [KSP]({{ "/en/glossary/ksp/" | relative_url }}).
- **Compatibility advantage**: kapt works with any Java annotation processor out of the box. If a library only supports Java annotation processing (no KSP backend), kapt is the only option.
- **Declared via Gradle plugin**: `plugins { id("org.jetbrains.kotlin.kapt") }`, then dependencies use `kapt(...)` instead of `implementation(...)` for processor artifacts.
- **Migration path**: Most major Android libraries ([Dagger]({{ "/en/glossary/dagger/" | relative_url }})/[Hilt]({{ "/en/glossary/hilt/" | relative_url }}), [Room]({{ "/en/glossary/room/" | relative_url }}), Moshi) now support [KSP]({{ "/en/glossary/ksp/" | relative_url }}). Google recommends migrating from kapt to KSP for faster builds. The migration is typically mechanical: replace `kapt(...)` with `ksp(...)` in `build.gradle.kts` and switch the processor artifact.
- **Deprecated status**: kapt is in maintenance mode. JetBrains recommends KSP for all new projects and actively encourages migration of existing ones.
