## The Theory (The What)

**KSP** (Kotlin Symbol Processing) is the modern [annotation processing]({{ "/en/glossary/annotation-processing/" | relative_url }}) API for Kotlin. Unlike [kapt]({{ "/en/glossary/kapt/" | relative_url }}), which generates Java [stubs]({{ "/en/glossary/stubs/" | relative_url }}) and runs Java processors, KSP operates directly on Kotlin's compiler symbols — it sees Kotlin code as Kotlin, understands Kotlin-specific features ([suspend functions]({{ "/en/glossary/suspend-functions/" | relative_url }}), [extension functions]({{ "/en/glossary/extension-functions/" | relative_url }}), nullability), and runs significantly faster.

```kotlin
// From FollowApp Suite — build.gradle.kts (core/data)
plugins {
    alias(libs.plugins.ksp)
    alias(libs.plugins.hilt.android)
}

dependencies {
    ksp(libs.hilt.compiler)
}
```

## The Senior Nuance

- **No stubs, no overhead**: KSP skips the Java stub generation that makes [kapt]({{ "/en/glossary/kapt/" | relative_url }}) slow. In practice this means ~2× faster [compile times]({{ "/en/glossary/compile-time/" | relative_url }}) for annotation processing — a meaningful difference in projects with many modules.
- **Kotlin-native API**: KSP processors work with `KSDeclaration`, `KSClassDeclaration`, `KSFunctionDeclaration` — types that directly model Kotlin constructs. This lets processors handle Kotlin features (nullability, default parameters, `value class`) correctly, which kapt cannot.
- **Incremental processing**: KSP supports incremental processing out of the box — only reprocesses files that changed. kapt's incremental support is limited and often disabled in practice.
- **Gradle DSL**: Processor dependencies use `ksp(...)` instead of `kapt(...)`. The FAS codebase uses KSP exclusively — [Hilt]({{ "/en/glossary/hilt/" | relative_url }})'s compiler and [Room]({{ "/en/glossary/room/" | relative_url }})'s compiler both run through KSP.
- **Multiplatform ready**: KSP works with Kotlin Multiplatform projects, while kapt is JVM-only.
