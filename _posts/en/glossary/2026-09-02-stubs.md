## The Theory (The What)

In the context of [annotation processing]({{ "/en/glossary/annotation-processing/" | relative_url }}), **stubs** are simplified Java source files generated from Kotlin code by [kapt]({{ "/en/glossary/kapt/" | relative_url }}). Since Java annotation processors only understand Java source, kapt must translate every Kotlin file into a Java stub — a skeleton with the correct class structure, method signatures, and annotations, but no implementation bodies. These stubs are then fed to the Java `javax.annotation.processing` API.

## The Senior Nuance

- **Stubs are the reason kapt is slow**: Generating a Java stub for every Kotlin source file is an expensive [compile-time]({{ "/en/glossary/compile-time/" | relative_url }}) step. In large codebases, stub generation alone can take longer than the actual annotation processing — it's the primary motivation for migrating to [KSP]({{ "/en/glossary/ksp/" | relative_url }}), which eliminates stubs entirely.
- **Stubs are lossy**: Kotlin features like `suspend`, default parameters, `value class`, and nullability annotations cannot be perfectly represented in Java stubs. This means kapt-based processors may see an incomplete picture of the Kotlin code.
- **Not the same as test stubs**: In testing, "stub" means a fake implementation that returns canned values. In annotation processing, "stub" is specifically the generated Java skeleton. Context determines meaning.
- **KSP solves the problem**: [KSP]({{ "/en/glossary/ksp/" | relative_url }}) reads Kotlin compiler symbols directly, so no Java translation is needed. The processor sees Kotlin code as Kotlin — with full nullability, suspend, and extension information preserved.
