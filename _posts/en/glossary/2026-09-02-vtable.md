## The Theory (The What)

A **vtable** (virtual method table) is a data structure the [JVM]({{ "/en/glossary/jvm/" | relative_url }}) maintains for every class that has `open` (overridable) methods. It is an array of function pointers — one entry per virtual method — that maps each method signature to the concrete implementation for that class. When [virtual dispatch]({{ "/en/glossary/virtual-dispatch/" | relative_url }}) occurs, the [JVM]({{ "/en/glossary/jvm/" | relative_url }}) reads the object's class pointer, looks up the vtable at a fixed index for that method, and jumps to the implementation. This is how [polymorphism]({{ "/en/glossary/polymorphism/" | relative_url }}) works at the hardware level.

```
// Conceptual vtable layout (not real Kotlin syntax)

Dog vtable:
  [0] toString()  → Dog.toString()
  [1] hashCode()  → Any.hashCode()   // inherited, not overridden
  [2] sound()     → Dog.sound()      // overridden — points to Dog's impl

Animal vtable:
  [0] toString()  → Any.toString()
  [1] hashCode()  → Any.hashCode()
  [2] sound()     → Animal.sound()   // base implementation
```

When `animal.sound()` is called, the [JVM]({{ "/en/glossary/jvm/" | relative_url }}) reads `animal`'s class, accesses slot `[2]` in the vtable, and finds `Dog.sound()` if the actual object is a `Dog`.

## The Senior Nuance

- The vtable lookup is a single pointer indirection — constant time, not a search. This is why virtual dispatch is fast. The [JVM]({{ "/en/glossary/jvm/" | relative_url }})'s [JIT compiler]({{ "/en/glossary/jit-compilation/" | relative_url }}) further optimizes monomorphic call sites by inlining the concrete method directly, eliminating even the pointer hop.
- Kotlin's `final`-by-default design (classes and methods are `final` unless marked `open`) means the compiler can often skip the vtable entirely. A call to a `final` method is a direct call — [static dispatch]({{ "/en/glossary/static-dispatch/" | relative_url }}) at the [bytecode]({{ "/en/glossary/bytecode/" | relative_url }}) level.
- Interfaces use a separate mechanism (itable or interface method table) because a class can implement many interfaces, and the method's slot position may differ across classes. The itable lookup involves a search for the correct interface, then an index into that interface's method table — slightly more expensive than a vtable index.
- [Extension functions]({{ "/en/glossary/extension-functions/" | relative_url }}) bypass the vtable completely. They compile to static methods where the [receiver]({{ "/en/glossary/receiver-type/" | relative_url }}) is the first parameter — no polymorphism, no indirection, no vtable involvement.
