## The Theory (The What)

A **backing field** is the actual storage slot that a property uses behind its getter and setter. In Kotlin, properties have an implicit backing field generated by the compiler whenever at least one accessor uses the `field` identifier. You access it with the `field` keyword inside a custom `get()` or `set()`:

```kotlin
var name: String = "default"
    set(value) {
        field = value.trim()
    }
```

If neither accessor references `field`, no backing field is generated — the property is purely computed. When a property uses [delegated properties]({{ "/en/01-kotlin-core/delegated-properties/" | relative_url }}) (`by`), the delegate object replaces the backing field entirely: the compiler generates a hidden field that holds the delegate instance, not the property value.

At the [bytecode]({{ "/en/glossary/bytecode/" | relative_url }}) level, a backing field is a private [JVM]({{ "/en/glossary/jvm/" | relative_url }}) field. The `lateinit` modifier keeps the backing field nullable internally while exposing a non-nullable type to callers — accessing it before initialization triggers `UninitializedPropertyAccessException` via a compiler-inserted null-check.

## The Senior Nuance

- A Senior knows that `field` is only available inside the property's own accessors — it is not a general [keyword]({{ "/en/glossary/keyword/" | relative_url }}) and cannot be used elsewhere. Attempting to reference a property's backing field from outside its accessor requires [Runtime Reflection]({{ "/en/glossary/runtime-reflection/" | relative_url }}).
- The backing property pattern (`private var _items` + public `val items get() = _items`) is common for exposing read-only views of mutable state. In [MVI]({{ "/en/glossary/mvi-pattern/" | relative_url }}) ViewModels, this is the standard pattern for [protected state]({{ "/en/glossary/protected-state/" | relative_url }}): `private val _uiState = MutableStateFlow(...)` with a public `val uiState: StateFlow<T> = _uiState.asStateFlow()`.
- When a property's custom setter uses `field = value`, it stores the value directly. When it calls `this.property = value` instead, it recursively calls the setter — a common mistake that causes a `StackOverflowError`.
