## The Theory (The What)

**`@Stable`** is a Compose annotation that promises the compiler a type's public properties will notify Compose when they change. This contract enables Compose to **skip recomposition** of [`@Composable`]({{ "/en/glossary/composable/" | relative_url }}) functions when their `@Stable` parameters haven't changed.

The `@Stable` contract requires:

1. `equals()` always returns the same result for the same two instances.
2. When a public property changes, Compose is notified (via the snapshot system).
3. All public properties are either [primitive]({{ "/en/glossary/primitives/" | relative_url }}) types or themselves `@Stable`.

Classes that use [delegated properties]({{ "/en/01-kotlin-core/delegated-properties/" | relative_url }}) backed by `mutableStateOf()` fulfill this contract naturally: the snapshot system notifies Compose of every write.

```kotlin
@Stable
class CounterState {
    var count by mutableStateOf(0)
        private set

    fun increment() { count++ }
}
```

Compose also has `@Immutable` — a stricter guarantee that all properties will never change after construction. `@Stable` is the weaker, more common contract: properties can change, but Compose will know.

## The Senior Nuance

- A Senior knows that the Compose compiler plugin automatically infers stability for many types — `data class` with all stable fields, primitive types, `String`, `List<Stable>`. The `@Stable` annotation is only necessary when the compiler cannot prove stability (e.g., classes with interfaces as properties, or types from non-Compose modules). Use the Compose Compiler Metrics (`-Pcompose.compiler.metricsDestination`) to check which classes are stable.
- `@Stable` classes holding `by mutableStateOf()` are the standard pattern for multi-property state holders that live outside the composition — like the `ReorderState` in drag-and-drop controllers. Unlike `remember { mutableStateOf() }` which is scoped to a single composable, a `@Stable` instance can be shared across the composable tree.
- Marking a class `@Stable` when it does not truly satisfy the contract (mutable properties without snapshot backing) causes **skipped recompositions on stale data** — one of the hardest Compose bugs to diagnose because the UI silently stops updating.
- In multi-module projects, the Compose compiler cannot see into non-Compose modules. Types from these modules are treated as unstable by default, forcing recomposition even when values haven't changed. The fix is either adding `@Stable` to those types or creating a stability configuration file.
