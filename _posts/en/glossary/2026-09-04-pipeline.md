## The Theory (The What)

A **pipeline** is a chain of [data transformations]({{ "/en/glossary/data-transformation/" | relative_url }}) where the output of one step becomes the input of the next. In Kotlin, pipelines are expressed through chained function calls — [collection operators]({{ "/en/glossary/collection-operators/" | relative_url }}), [scope functions]({{ "/en/01-kotlin-core/scope-functions/" | relative_url }}), or Flow operators — that read top-to-bottom as a sequence of transformations.

In Android architecture, the [Mapper pattern]({{ "/en/glossary/mapper-pattern/" | relative_url }}) forms a pipeline across [data layers]({{ "/en/glossary/data-layer/" | relative_url }}):

```
NetworkResponse → Entity → DomainModel → UiState
```

Each stage has a dedicated [mapper function]({{ "/en/glossary/mapper-function/" | relative_url }}) that converts between models, keeping layers decoupled.

## The Senior Nuance

- A Senior designs pipelines so each stage is independently testable. A Flow pipeline like `dao.getAll().map { it.toDomain() }.map { toUiState(it) }` can be tested at each step in isolation.
- Pipeline ordering matters for performance: `filter` before `map` reduces the number of transformations; `distinctUntilChanged` before an expensive transformation avoids redundant work.
- Kotlin offers two pipeline styles with different performance profiles: eager [collections]({{ "/en/glossary/collections/" | relative_url }}) (`list.filter { }.map { }`) create intermediate collections at each step; `Sequence` and Flow evaluate lazily, processing one element at a time through the entire chain. A Senior picks the right tool based on collection size and transformation cost.
