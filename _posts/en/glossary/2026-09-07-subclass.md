## The Theory (The What)

A **subclass** is a class that derives from another (its *superclass* or parent), inheriting its members and optionally specialising them with `override`. The subclass is a *subtype*: any reference to the parent can hold a subclass instance, which is what makes [polymorphism]({{ "/en/glossary/polymorphism/" | relative_url }}) possible.

In Kotlin, classes are [`final`]({{ "/en/glossary/final/" | relative_url }}) by default. Subclassing requires the parent to opt in with `open`:

```kotlin
// From FollowApp Suite — TrashPreferences.kt
@Singleton
open class TrashPreferences @Inject constructor(
    private val dataStore: DataStore<Preferences>
) {
    open fun skipDeleteConfirmation(): Flow<Boolean> = dataStore.data.map { prefs ->
        prefs[skipDeleteConfirmKey] ?: false
    }
}
```

A [sealed hierarchy]({{ "/en/glossary/sealed-hierarchy/" | relative_url }}) is the constrained form: the set of subclasses is fixed and known to the compiler.

```kotlin
// From FollowApp Suite — StateChip.kt
sealed interface ChipState {
    val foreground: Color @Composable get
    @Composable fun inputColors(): SelectableChipColors
}

object Full : ChipState {
    override val foreground: Color
        @Composable get() = MaterialTheme.colorScheme.onPrimaryContainer

    @Composable
    override fun inputColors(): SelectableChipColors = /* ... */
}
```

## The Senior Nuance

- **`open` is a design decision, and often a testing one.** `TrashPreferences` is `open` not because anything extends it in production, but so tests can substitute a fake. A Senior notices that `open` for mockability is a smell that an interface would solve more honestly — and that libraries like MockK can mock [`final`]({{ "/en/glossary/final/" | relative_url }}) classes anyway.
- **Subclassing is the tightest coupling available.** A subclass depends on its parent's implementation, not just its contract, so a change in the parent silently changes every subclass. This is the fragile base class problem, and it is why Kotlin made [`final`]({{ "/en/glossary/final/" | relative_url }}) the default.
- **[`final`]({{ "/en/glossary/final/" | relative_url }}) subclasses are faster.** When a method cannot be overridden, the [JIT compiler]({{ "/en/glossary/jit-compilation/" | relative_url }}) can devirtualise it — turning [virtual dispatch]({{ "/en/glossary/virtual-dispatch/" | relative_url }}) through the [vtable]({{ "/en/glossary/vtable/" | relative_url }}) into [static dispatch]({{ "/en/glossary/static-dispatch/" | relative_url }}), and often inlining it outright.
- **Subclass ≠ subtype in the generic case.** `Dog` is a subtype of `Animal`, but `Box<Dog>` is *not* a subtype of `Box<Any>` unless the class declares [covariance]({{ "/en/glossary/covariance/" | relative_url }}) with `out`. Conflating the two is one of the most common generics mistakes.
- **Prefer composition and delegation.** Kotlin's `by` [delegation]({{ "/en/glossary/by-delegation/" | relative_url }}) gives you interface reuse without [inheritance]({{ "/en/glossary/inheritance/" | relative_url }})'s coupling — the reason it exists as a first-class [keyword]({{ "/en/glossary/keyword/" | relative_url }}).
