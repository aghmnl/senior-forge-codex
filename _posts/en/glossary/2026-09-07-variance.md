## The Theory (The What)

**Variance** answers one question: if `Cat` is a subtype of `Animal`, what is the relationship between `Box<Cat>` and `Box<Animal>`? There are three possible answers, and Kotlin has a [keyword]({{ "/en/glossary/keyword/" | relative_url }}) for each:

| Variance | Declaration | Subtyping | Type appears in |
|----------|-------------|-----------|-----------------|
| [Invariance]({{ "/en/glossary/invariance/" | relative_url }}) (default) | `Box<T>` | no relationship | both positions |
| [Covariance]({{ "/en/glossary/covariance/" | relative_url }}) | `Box<out T>` | `Box<Cat>` <: `Box<Animal>` | [return types]({{ "/en/glossary/return-type/" | relative_url }}) only |
| [Contravariance]({{ "/en/glossary/contravariance/" | relative_url }}) | `Box<in T>` | `Box<Animal>` <: `Box<Cat>` | parameters only |

The rule that decides which one you are allowed to use is purely **positional**. If the [generic type parameter]({{ "/en/glossary/generic-type-parameters/" | relative_url }}) is produced (returned), it can be `out`. If it is consumed (accepted as a parameter), it can be `in`. If both, it must stay [invariant]({{ "/en/glossary/invariance/" | relative_url }}).

## The Senior Nuance

- **Declaration-site variance is Kotlin's headline improvement over Java.** You annotate the class once (`interface Producer<out T>`) and every [call site]({{ "/en/glossary/call-site/" | relative_url }}) benefits. Java only has *use-site* variance — wildcards like `List<? extends Animal>` — which every caller must restate. Kotlin supports use-site variance too (`fun copy(from: Array<out Any>)`, called a type projection) for the cases where a class cannot be made variant globally.
- **[Immutability]({{ "/en/glossary/immutability/" | relative_url }}) is what makes covariance sound.** Kotlin's `List<out E>` is covariant precisely because it has no `add`. `MutableList<E>` is [invariant]({{ "/en/glossary/invariance/" | relative_url }}) because it does. Reading the [collections]({{ "/en/glossary/collections/" | relative_url }}) hierarchy through the variance lens explains the whole read-only/mutable split.
- **Function types are already variant.** `(T) -> R` compiles to `Function1<in P1, out R>`: contravariant in its parameter, covariant in its result. Every callback in a generic API inherits this for free, which is why a `(Any) -> String` can be passed where a `(Task) -> String` is expected.
- **Variance is a public promise.** Declaring `out` tells every caller "this type will never be consumed here". Adding a consuming method later is a breaking API change, not a refactor. Choose variance when designing the interface, not when a compile error appears.
- **The `@UnsafeVariance` escape hatch exists and is a smell.** Kotlin's own `List<out E>.contains(element: @UnsafeVariance E)` uses it because `contains` is logically safe despite being an in position. Reaching for it in application code almost always means the class should have stayed [invariant]({{ "/en/glossary/invariance/" | relative_url }}).
