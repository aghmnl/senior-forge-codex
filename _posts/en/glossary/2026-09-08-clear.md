## The Theory (The What)

**`clear()`** removes every element from a `MutableCollection` or [`MutableMap`]({{ "/en/glossary/mutable-map/" | relative_url }}) in place, leaving the same instance empty. It mutates the object, so every holder of that reference sees the result.

```kotlin
// From FollowApp Suite — TasksScreen.kt
if (localIds != remoteIds) {
    localTasks.clear()
    localTasks.addAll(uiState.activeTasks)
}
```

## The Senior Nuance

- `clear()` + `addAll()` is the correct re-sync for a [`mutableStateListOf`]({{ "/en/glossary/mutable-state-list-of/" | relative_url }}): the identity of the observable list must survive, so it is emptied rather than replaced. For an ordinary state holder, assigning a brand-new [`List`]({{ "/en/glossary/list/" | relative_url }}) is safer, because it cannot be observed half-cleared.
- It does not shrink the backing array of an [`ArrayList`]({{ "/en/glossary/arraylist/" | relative_url }}) — capacity is retained. Good for reuse in [hot loops]({{ "/en/glossary/hot-loops/" | relative_url }}), a slow leak if a long-lived list is repeatedly filled with thousands of entries and cleared.
- Because it empties an object rather than producing a new value, `clear()` on shared state is a [concurrency]({{ "/en/glossary/concurrency/" | relative_url }}) hazard: another thread iterating that list sees it drain mid-pass.
