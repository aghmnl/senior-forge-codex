## The Theory (The What)

**`contains(element)`** answers membership, and Kotlin exposes it through the `in` [operator]({{ "/en/glossary/operator-overloading/" | relative_url }}): `x in collection` compiles to `collection.contains(x)`. Its cost depends entirely on the structure — `O(n)` on a [`List`]({{ "/en/glossary/list/" | relative_url }}), `O(1)` on a [`Set`]({{ "/en/glossary/sets/" | relative_url }}) or [`Map`]({{ "/en/glossary/maps/" | relative_url }}) key set.

```kotlin
// From FollowApp Suite — TasksViewModel.kt
val assignedValues = options.toSet()          // hoisted out of the loop
val unassigned = tasks.filter { task ->
    val value = (task.customLabels[groupBy] as? LabelValue.Scale)?.value
    value == null || value !in assignedValues // O(1) per task
}
```

## The Senior Nuance

- `in` hides the complexity, which is why the `O(n·m)` filter is the most common performance bug in Android code. The same expression is `O(1)` or `O(n)` depending on one earlier [`toSet`]({{ "/en/glossary/to-set/" | relative_url }}) call.
- It compares with [`equals`]({{ "/en/glossary/equals/" | relative_url }}), so a [data class]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}) with an unstable field (a timestamp, a transient flag) will silently fail a membership test you expected to pass.
- `in` also resolves to `contains` on ranges and `String` — `groupBy in availableScales` on a [`Map`]({{ "/en/glossary/maps/" | relative_url }}) checks *keys*, not values, which reads naturally but surprises people who expect `values`.
