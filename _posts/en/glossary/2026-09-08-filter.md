## The Theory (The What)

**`filter { }`** returns a new [`List`]({{ "/en/glossary/list/" | relative_url }}) with the elements matching a predicate. `filterNot` is its inverse, `filterIsInstance<T>()` narrows by type, and `filterKeys`/`filterValues` do the same over a [`Map`]({{ "/en/glossary/maps/" | relative_url }}).

```kotlin
// From FollowApp Suite — TasksViewModel.kt
val done = tasks.filter { it.isCompleted }
val notDone = tasks.filter { !it.isCompleted }

// From FollowApp Suite — TasksUiState.kt
val selectedTasks: List<Task> get() = activeTasks.filter { it.id in selectedTaskIds }
```

## The Senior Nuance

- The predicate's cost is the operator's cost, multiplied by `n`. `it.id in selectedTaskIds` is `O(1)` because `selectedTaskIds` is a [`Set`]({{ "/en/glossary/sets/" | relative_url }}); the same line over a `List` would make the whole filter `O(n·m)` — the most common jank source in a list screen.
- Two `filter` passes to produce complementary groups (as above) walk the list twice; `partition { }` does it in one and returns both halves. With small lists the clarity usually wins, which is a judgement call worth making consciously.
- It always allocates. When `filter` feeds `first`/`any`, the [terminal operations]({{ "/en/glossary/terminal-operations/" | relative_url }}) `firstOrNull { }`/`any { }` short-circuit without building a list at all — and over a [`Sequence`]({{ "/en/glossary/sequences/" | relative_url }}) the whole chain stops at the first match.
