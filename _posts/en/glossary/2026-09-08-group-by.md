## The Theory (The What)

**`groupBy { }`** returns a `Map<K, List<T>>` keyed by the selector's result, with every element collected into its bucket. `groupBy(keySelector, valueTransform)` maps the values on the way in, and `groupingBy { }` starts a lazy grouping for folds and counts.

```kotlin
// From FollowApp Suite — LabelRepositoryImpl.kt
val optionsByLabelId = allOptions.groupBy { it.labelId }
labels.associate { labelEntity ->
    val label = labelEntity.toDomain()
    val options = (optionsByLabelId[labelEntity.id] ?: emptyList()).map { it.toDomain() }
    label to options
}
```

## The Senior Nuance

- This is the fix for the join-in-a-loop antipattern. Grouping once and looking each key up is `O(n + m)`; calling `allOptions.filter { it.labelId == id }` inside a loop over labels is `O(n·m)`.
- It is eager and allocates a [`Map`]({{ "/en/glossary/maps/" | relative_url }}) plus one [`List`]({{ "/en/glossary/list/" | relative_url }}) per key, so it forces a [`Sequence`]({{ "/en/glossary/sequences/" | relative_url }}) chain to materialise. For counting, `groupingBy { }.eachCount()` avoids building the intermediate lists entirely.
- Keys are compared with [`equals`]({{ "/en/glossary/equals/" | relative_url }}) and hashed, so a selector returning a [data class]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}) works, while one returning a mutable object silently produces duplicate buckets. Iteration order of the result follows first-encounter order (`LinkedHashMap`).
