## The Theory (The What)

`copy()` is the function the compiler generates for every [`data class`]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}). It creates a **new instance** with the same property values, overriding only the named arguments. It is how an immutable state object "changes": it does not — a new one replaces it.

```kotlin
// From FollowApp Suite — TasksViewModel.kt
_uiState.update { it.copy(form = it.form.copy(title = title)) }
```

## The Senior Nuance

- `copy()` is a **shallow copy**. The new instance shares every referenced object with the old one — [structural sharing]({{ "/en/glossary/structural-sharing/" | relative_url }}) — so copying a state class with thirty properties allocates one small object, not thirty. That is what makes per-keystroke state updates cheap.
- Shallow also means the guarantee only goes as deep as the types allow. `copy()` on a state holding a `MutableList` hands the new instance the *same* list; both objects now alias one mutable buffer, and [`equals`]({{ "/en/glossary/equals/" | relative_url }}) can report "unchanged" while the contents differ. Immutability has to hold all the way down.
- `copy()` ignores properties declared outside the primary constructor, and it does **not** run `init` blocks with validation logic on the copied path in the way a constructor call would look — so invariants enforced only by a factory function can be bypassed by `copy()`. For state classes this is rarely a problem; for domain models with validated construction it is a real hole.
