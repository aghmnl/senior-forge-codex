## The Theory (The What)

`MutableStateFlow.update {}` applies a transformation to the current value **atomically**. It reads the value, runs your lambda, and publishes the result only if nothing changed in between — retrying with the fresh value otherwise. It is the correct way to express "new state = f(old state)".

```kotlin
// From FollowApp Suite — TasksViewModel.kt
fun onTaskSelectionToggled(taskId: String) {
    _uiState.update {
        val updated = if (taskId in it.selectedTaskIds) {
            it.selectedTaskIds - taskId
        } else {
            it.selectedTaskIds + taskId
        }
        it.copy(selectedTaskIds = updated)
    }
}
```

## The Senior Nuance

- The rule is mechanical: **if the new value mentions the old value, use `update`; if it does not, `value =` is fine.** `_uiState.value = TasksUiState()` is a plain publish. `_uiState.value = _uiState.value.copy(...)` is a [race condition]({{ "/en/glossary/race-condition/" | relative_url }}) waiting for a slow frame.
- The lambda may run several times because of the [compare-and-set]({{ "/en/glossary/compare-and-set/" | relative_url }}) retry, so it must be **pure**: no logging, no analytics, no navigation, no repository calls. Compute the next state, return it, and do the side effects after.
- `update` composes for nested state without breaking [atomicity]({{ "/en/glossary/atomicity/" | relative_url }}), because the nested [`copy`]({{ "/en/glossary/copy/" | relative_url }}) happens inside the block: `_uiState.update { it.copy(form = it.form.copy(title = title)) }`. Reading `_uiState.value.form` *outside* the block and passing it in reintroduces the race you were avoiding.
