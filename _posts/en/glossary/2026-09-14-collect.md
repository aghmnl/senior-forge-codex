## The Theory (The What)

**`collect { }`** is the terminal [suspend function]({{ "/en/glossary/suspend-functions/" | relative_url }}) on a [`Flow`]({{ "/en/glossary/flow/" | relative_url }}): it starts the flow, receives every emitted value in the lambda, and does not return until the flow completes — which for a `StateFlow` or a Room query flow is never. It must therefore run inside a coroutine whose [lifecycle]({{ "/en/glossary/lifecycle/" | relative_url }}) bounds it.

```kotlin
// From FollowApp Suite — PremiumRepositoryImpl.kt
scope.launch {
    billingConnector.isOwned
        .filterNotNull()
        .collect { owned -> premiumPreferences.setAdsRemoved(owned) }
}
```

## The Senior Nuance

- **`collect` suspends forever on hot flows.** Anything written after it in the same coroutine never runs. Two flows need two `launch`es, or `combine`.
- **It runs on the collector's dispatcher.** Upstream operators run there too unless `flowOn` moves them; the lambda always runs where `collect` was called.
- **An exception in the lambda cancels the collection** and propagates to the coroutine — with a [`SupervisorJob`]({{ "/en/glossary/supervisor-job/" | relative_url }}) and no [`CoroutineExceptionHandler`]({{ "/en/glossary/coroutine-exception-handler/" | relative_url }}), that is a crash. `catch { }` upstream handles emitter errors, not collector errors.
- **In UI, prefer `collectAsStateWithLifecycle()` or `repeatOnLifecycle`** over a raw `collect` in `lifecycleScope`, so collection stops when the screen is not visible.
- See [Context & Dispatchers]({{ "/en/02-coroutines-flow/context-dispatchers/" | relative_url }}).
