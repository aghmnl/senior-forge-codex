## The Theory (The What)

**`kotlin.Result<T>`** is the standard-library type that holds either a success value or a `Throwable`. `runCatching { }` produces one; `getOrNull()`, `getOrDefault()`, `getOrThrow()`, `onSuccess { }`, `onFailure { }`, `map { }` and `fold(...)` consume it. It turns an exception into a value the caller must look at, instead of one that unwinds the stack.

```kotlin
// From FollowApp Suite — BackupManager.kt
suspend fun exportTo(uri: Uri): Result<Unit> = withContext(Dispatchers.IO) {
    runCatching {
        // ... write file
    }.onSuccess {
        Log.d(TAG, "Backup exported")
    }.onFailure { Log.e(TAG, "Backup export failed", it) }
}
```

The [return type]({{ "/en/glossary/return-type/" | relative_url }}) `Result<Unit>` tells the ViewModel that export can fail in expected ways it should present, not crash on.

## The Senior Nuance

- **`runCatching` catches everything — including [`CancellationException`]({{ "/en/glossary/cancellation-exception/" | relative_url }}).** In a coroutine that turns a cancelled scope into one that keeps working. Rethrow it: `.onFailure { if (it is CancellationException) throw it }`, or catch specific types with a plain [`try/catch`]({{ "/en/glossary/try-catch/" | relative_url }}).
- **Use it for expected failure, not for bugs.** "File could not be opened" is a `Result`; a `NullPointerException` from a broken [invariant]({{ "/en/glossary/invariant/" | relative_url }}) should crash loudly.
- **A sealed hierarchy is often better for domain errors** — `Result` carries only a `Throwable`, so callers must `is`-check exception classes to branch. A `sealed interface ExportError` documents the cases.
- It is a value class over `Any?`: cheap, but historically restricted as a direct return type (lifted in Kotlin 1.5).
