## The Theory (The What)

**`try { } catch (e: T) { } finally { }`** is Kotlin's structured exception handling. `try` is an *expression* — it yields the value of the last line of whichever block ran — and `finally` always executes, including on cancellation. Catching by type is the whole design: catch the exceptions you can handle, let the rest propagate.

```kotlin
// From FollowApp Suite — SettingsViewModel.kt
viewModelScope.launch {
    try {
        val session = googleAuthClient.signIn(activityContext)
        saveUserSessionUseCase(session)
    } catch (e: GetCredentialCancellationException) {
        Log.d(TAG, "Google sign-in cancelled by user")
    } catch (e: GetCredentialException) {
        _uiState.update { it.copy(messageRes = R.string.error_sign_in) }
    }
}
```

Two `catch` clauses, two decisions: user cancellation is not an error; a real failure becomes UI state.

## The Senior Nuance

- **`catch (e: Exception)` in a coroutine swallows [`CancellationException`]({{ "/en/glossary/cancellation-exception/" | relative_url }}).** The coroutine then continues after it was told to stop. Catch specific types, or rethrow: `if (e is CancellationException) throw e`.
- **`finally` runs on cancellation too.** That is what makes it the place for cleanup — and why cleanup that itself suspends needs `withContext(NonCancellable)`.
- **Kotlin has no checked exceptions.** Nothing forces a caller to catch; the signature does not say what can be thrown. [`Result`]({{ "/en/glossary/result/" | relative_url }}) or a sealed error type is how you make failure visible in the type.
- **Do not catch to log and rethrow at every layer.** One handler at the boundary that owns the decision; everything below lets it propagate.
