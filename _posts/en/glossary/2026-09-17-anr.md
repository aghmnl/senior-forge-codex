## The Theory (The What)

An **ANR** (*Application Not Responding*) is the system dialog — and the process kill behind it — that Android raises when the [main thread]({{ "/en/glossary/main-thread/" | relative_url }}) stays busy too long: about **5 seconds** without processing an input event, 10–20 seconds for a `BroadcastReceiver`, 20 seconds for a foreground `Service`. It is the terminal form of a [blocking call]({{ "/en/glossary/blocking-call/" | relative_url }}) on Main. ANR rate is one of the Play Console's core vitals; too many and the app is demoted in search and recommendations.

```kotlin
// From FollowApp Suite — TasksViewModel.kt
// Date math off the main thread: pattern scans over months/years
// must never stall input dispatching (popup ANR)
val suggested = withContext(Dispatchers.Default) { /* ... */ }
```

## The Senior Nuance

- **The clock starts at the input event, not at your code.** A 4-second block right after the user taps is an ANR if the next tap lands during it. Budget in *frames*, not seconds — see [jank]({{ "/en/glossary/jank/" | relative_url }}).
- **A coroutine on Main does not protect you.** [`runBlocking`]({{ "/en/glossary/run-blocking/" | relative_url }}), `Thread.sleep`, a synchronous [SDK]({{ "/en/glossary/sdk/" | relative_url }}) bootstrap or a `File.readText()` inside `viewModelScope.launch` all still block Main. Main-safety is about where the *work* runs, not about which builder wraps it.
- **Diagnose with the ANR trace, not by guessing.** `/data/anr/traces.txt` (or Play Console's ANR page) shows exactly which frame of the main thread was stuck; [profiling]({{ "/en/glossary/profiling/" | relative_url }}) and [`StrictMode`]({{ "/en/glossary/strict-mode/" | relative_url }}) catch it earlier in development.
