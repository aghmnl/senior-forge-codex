## The Theory (The What)

**Jank** is a visible stutter: a frame that missed its deadline, so the screen shows the previous frame again. At 60 Hz every frame has ~**16.6 ms** to be measured, laid out, drawn and composited — all on the [main thread]({{ "/en/glossary/main-thread/" | relative_url }}); at 120 Hz it is ~8.3 ms. Any work on Main that exceeds that budget drops frames. Jank is the *small* version of a [blocking call]({{ "/en/glossary/blocking-call/" | relative_url }}) on Main; an [ANR]({{ "/en/glossary/anr/" | relative_url }}) is the large one.

```kotlin
// Not found in FAS — standalone example
// 40 ms of JSON parsing on Main during a scroll = 2–3 dropped frames per item
LazyColumn { items(rows) { row -> Text(parseHeavy(row)) } }   // parse off Main instead
```

## The Senior Nuance

- **Jank is cumulative.** Ten 5 ms tasks in one frame jank as much as one 50 ms task. `Choreographer` and Perfetto show the frame timeline; Play Console reports "slow rendering" as a vital.
- **Not only I/O causes it.** Layout passes over deep hierarchies, allocation-heavy loops, and [recomposition]({{ "/en/glossary/recomposition/" | relative_url }}) storms are all Main-thread time. The fix is not always [`withContext`]({{ "/en/glossary/with-context/" | relative_url }}); sometimes it is doing less work.
- **The user notices at ~2 dropped frames.** Which is why "it's only 30 ms" is not a defence.
