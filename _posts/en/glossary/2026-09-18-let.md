## The Theory (The What)

**`let`** is a [Scope Functions]({{ "/en/01-kotlin-core/scope-functions/" | relative_url }}) scope function: `x.let { it -> ... }` calls the lambda with `x` as `it` and returns the lambda's result. Combined with a [safe call]({{ "/en/glossary/safe-call/" | relative_url }}) — `x?.let { ... }` — the block runs only when `x` is not [`null`]({{ "/en/glossary/null/" | relative_url }}), and inside it `it` is non-null. That makes `?.let` the idiomatic way to "do something with this value if present" in [Null Safety: Elvis & Safe Calls]({{ "/en/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}), and the reason it appears in the strategies for eliminating `!!`. Its sibling [`run`]({{ "/en/glossary/run/" | relative_url }}) does the same with `this` as the receiver.

```kotlin
// From FollowApp Suite — AuthPreferences
// Safe call + let + Elvis: save when present, remove when absent
fun saveSession(session: UserSession, prefs: MutablePreferences) {
    session.photoUrl?.let { prefs[photoUrlKey] = it }
        ?: prefs.remove(photoUrlKey)
}
```

## The Senior Nuance

- **`let` returns the block's value — that is its power and its trap.** `x?.let { transform(it) }` maps a nullable in one line; but `x?.let { ... } ?: fallback` runs the fallback *also* when the block itself returns null. The FAS example above is safe because the assignment returns `Unit`.
- **Prefer `let` for transformations, `if` for branching.** `if (x != null) { ... } else { ... }` is clearer than a `let`/Elvis chain when both branches have logic; `let` shines when you need the result.
- **Name the parameter when nesting.** `it` inside `it` is unreadable: `user?.let { u -> u.address?.let { a -> ... } }`.
- See [Null Safety: Elvis & Safe Calls]({{ "/en/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}) and [Scope Functions]({{ "/en/01-kotlin-core/scope-functions/" | relative_url }}).
