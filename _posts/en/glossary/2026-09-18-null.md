## The Theory (The What)

**`null`** is the literal that means "no value". In Kotlin it is only assignable to *nullable* types — those written with a trailing `?` such as [`String?`]({{ "/en/glossary/string/" | relative_url }}) — and the compiler rejects `val s: String = null` at [compile time]({{ "/en/glossary/compile-time/" | relative_url }}). That single rule turns the [`NullPointerException`]({{ "/en/glossary/null-pointer-exception/" | relative_url }}) from a runtime surprise into a type error, and makes `null` a deliberate part of an API's contract: a `T?` says "this may legitimately be absent", a `T` says "this is always here". Everything in [Null Safety: Elvis & Safe Calls]({{ "/en/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}) — [`?.`]({{ "/en/glossary/safe-call/" | relative_url }}), [`?:`]({{ "/en/glossary/elvis-operator/" | relative_url }}), [`as?`]({{ "/en/glossary/as-safe-cast/" | relative_url }}) — exists to move a value from `T?` to `T` explicitly.

```kotlin
// Not found in FAS — standalone example
val email: String = "a@b.c"      // never null: the compiler enforces it
val photoUrl: String? = null     // legitimately absent

// val bad: String = null        // does not compile
val length = photoUrl?.length ?: 0
```

## The Senior Nuance

- **`null` is data, not an error.** Model it where absence is meaningful (optional photo, unset preference) and forbid it where it is not (an ID, an email). Making everything nullable "just in case" pushes a null check onto every consumer.
- **`null` is a type of its own: `Nothing?`.** That is why `null` can be assigned to any `T?` and why `listOf(null)` infers `List<Nothing?>`.
- **The remaining NPE sources are at the edges.** [Platform types]({{ "/en/glossary/platform-types/" | relative_url }}) from Java, `!!`, and `lateinit` reads before init are where `null` still crashes a Kotlin app; treat those boundaries explicitly.
