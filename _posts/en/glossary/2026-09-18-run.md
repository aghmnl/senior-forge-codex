## The Theory (The What)

**`run`** is a [Scope Functions]({{ "/en/01-kotlin-core/scope-functions/" | relative_url }}) scope function that executes a lambda with the object as `this` and returns the lambda's result: `x.run { this.foo() }` or, as a non-extension, `run { ... }` to group statements into one expression. With a [safe call]({{ "/en/glossary/safe-call/" | relative_url }}) — `x?.run { ... }` — the block runs only when `x` is not [`null`]({{ "/en/glossary/null/" | relative_url }}), exactly like [`let`]({{ "/en/glossary/let/" | relative_url }}) but with receiver access instead of `it`, which is why [Null Safety: Elvis & Safe Calls]({{ "/en/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}) lists both as ways to handle the null case explicitly instead of using `!!`.

```kotlin
// Not found in FAS — standalone example
// run with receiver: configure and return a value in one expression
val request = connection?.run {
    connectTimeout = 5_000
    readTimeout = 10_000
    build()
} ?: return null

// run without receiver: several statements where an expression is expected
val label = run {
    val first = user.firstName.trim()
    val last = user.lastName.trim()
    "$first $last"
}
```

## The Senior Nuance

- **`run` vs `let` is `this` vs `it`.** Pick `run` when the block mostly calls members of the object (configuration, builders); pick `let` when the object is an argument you pass around. Mixing them randomly is the most common scope-function smell.
- **`run` returns the last expression, `apply` returns the receiver.** Use `run` when you need a computed result, `apply` when you want the configured object back.
- **The no-receiver `run { }` is an expression block.** It lets you keep a `val` single-assignment while computing it in several steps, which beats a `var` you mutate.
- See [Null Safety: Elvis & Safe Calls]({{ "/en/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}) and [Scope Functions]({{ "/en/01-kotlin-core/scope-functions/" | relative_url }}).
