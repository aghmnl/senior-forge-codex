## The Theory (The What)

**`hashCode`** returns the `Int` bucket index that hash-based collections — `HashMap`, [`HashSet`]({{ "/en/glossary/hash-set/" | relative_url }}), `LinkedHashMap` — use to find an object without scanning. Its contract is one rule: if two objects are [`equals`]({{ "/en/glossary/equals/" | relative_url }}), they must return the same `hashCode`; the reverse need not hold (collisions are normal). A [Data Classes: copy, equals, toString]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}) generates it from the [primary constructor]({{ "/en/glossary/primary-constructor/" | relative_url }}) properties, in lockstep with the generated `equals`, so the contract holds by construction.

```kotlin
// Not found in FAS — standalone example
data class TaskId(val value: String)          // equals + hashCode generated together

val seen = hashSetOf(TaskId("a"))
TaskId("a") in seen        // true: same hashCode → same bucket, then equals confirms

// Hand-written: both must change together, or the object gets lost in the set
class Broken(val id: String) {
    override fun equals(other: Any?) = other is Broken && other.id == id
    // no hashCode override → two equal objects land in different buckets
}
```

## The Senior Nuance

- **Breaking the contract loses objects, it does not throw.** An object whose `hashCode` changes after insertion (a mutable property in the hash) stays in the old bucket: `set.contains(x)` returns false for an `x` the set holds. The bug surfaces far from the cause.
- **Properties in the class body are excluded.** A data class with a `var timestamp` in the body hashes only the constructor properties — which is exactly what makes it safe as a map key, and surprising if you expected the timestamp to count.
- **Only stable, immutable properties belong in a hash.** That is the practical reason to declare data class properties as [`val`]({{ "/en/glossary/val/" | relative_url }}).
