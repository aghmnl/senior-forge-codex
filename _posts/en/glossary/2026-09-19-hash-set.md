## The Theory (The What)

**`HashSet`** is the JVM `Set` implementation backed by a hash table: `add`, `remove` and `contains` are amortised O(1) because it locates an element by its [`hashCode`]({{ "/en/glossary/hash-code/" | relative_url }}) bucket and then confirms with [`equals`]({{ "/en/glossary/equals/" | relative_url }}). It stores no order — `LinkedHashSet` (what `setOf`/`mutableSetOf` actually return) preserves insertion order. Its behaviour is the practical test of a [Data Classes: copy, equals, toString]({{ "/en/01-kotlin-core/data-classes/" | relative_url }})'s generated equality: two instances equal by the [primary constructor]({{ "/en/glossary/primary-constructor/" | relative_url }}) properties count as one element.

```kotlin
// Not found in FAS — standalone example
data class TaskId(val value: String) { var lastSeen: Long = 0 }

val ids = hashSetOf(TaskId("a").apply { lastSeen = 1 })
ids.add(TaskId("a").apply { lastSeen = 2 })   // false: lastSeen is in the body, so both are equal
ids.size                                       // 1
```

## The Senior Nuance

- **The set is only as correct as the element's `hashCode`.** Mutating a property that participates in the hash *after* insertion strands the element in the wrong bucket: it is in the set but `contains` says no. Elements of a hash set should be immutable.
- **`setOf` is not a `HashSet`.** Kotlin's `setOf`/`mutableSetOf` return `LinkedHashSet`, which keeps insertion order — a detail worth knowing when a test asserts on iteration order.
- **Data classes are the natural element type.** Generated `equals`/`hashCode` from `val` properties is exactly the contract a hash set needs; hand-written classes usually get it wrong.
