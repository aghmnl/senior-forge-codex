## The Theory (The What)

**`init`** is the initializer block that runs as part of construction, in the order it appears among the property initializers, after the [primary constructor]({{ "/en/glossary/primary-constructor/" | relative_url }}) parameters are bound. It is where a class validates its [invariants]({{ "/en/glossary/invariant/" | relative_url }}) — `init { require(interval > 0) }` — since the primary constructor has no body of its own. Its contents are *not* part of what a [Data Classes: copy, equals, toString]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}) generates: `init` does not affect [`equals`]({{ "/en/glossary/equals/" | relative_url }}), `hashCode` or `toString`.

```kotlin
// Not found in FAS — standalone example
data class RecurrenceRule(val frequency: Frequency, val interval: Int = 1) {
    init {
        require(interval > 0) { "interval must be > 0, was $interval" }
    }
}

RecurrenceRule(Frequency.WEEKLY, 0)              // throws IllegalArgumentException
```

## The Senior Nuance

- **`copy()` does re-run `init`, but it can still bypass factory-level validation.** A `copy()` goes through the constructor, so `init` checks apply; what it skips is any validation that lives only in a factory function or a private constructor. If construction is guarded, guard `copy` too — or make the constructor private and expose `create()`.
- **Keep `init` cheap and total.** It runs on every instantiation, including the thousands of `copy()` calls a state class sees per session. Heavy work or I/O in `init` is a hidden cost on every keystroke.
- **Order matters.** `init` blocks and property initializers execute top to bottom; reading a property declared below an `init` block gives you its default, not its initialized value.
