## The Theory (The What)

**`toString`** produces the textual representation of an object: `Any.toString` returns `ClassName@1a2b3c` (the type plus an identity hash), which tells a reader nothing. A [Data Classes: copy, equals, toString]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}) overrides it with `User(id=7, name=Ada)` — every [primary constructor]({{ "/en/glossary/primary-constructor/" | relative_url }}) property, in declaration order. It is what string templates (`"$user"`), `println` and most logging call implicitly.

```kotlin
// Not found in FAS — standalone example
data class User(val id: Int, val name: String) { var lastSeen: Long = 0 }

println(User(7, "Ada"))     // User(id=7, name=Ada)  — lastSeen is NOT shown

class Plain(val id: Int)
println(Plain(7))           // Plain@6d06d69c
```

## The Senior Nuance

- **The debugging payoff is the main reason to reach for a data class on a model.** A crash report or a log line with `RecurrenceRule(frequency=WEEKLY, interval=2, ...)` beats `RecurrenceRule@3f2a` by an enormous margin.
- **Same exclusion rule as [`equals`]({{ "/en/glossary/equals/" | relative_url }}).** Properties declared in the class body do not appear. If a field matters for debugging, it belongs in the primary constructor — or you override `toString` by hand.
- **Never log a data class holding secrets.** The generated `toString` prints tokens, passwords and emails verbatim; override it for those types, or keep sensitive fields out of the constructor.
- See [Data Classes: copy, equals, toString]({{ "/en/01-kotlin-core/data-classes/" | relative_url }}).
