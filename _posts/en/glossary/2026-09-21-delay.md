## The Theory (The What)

**`delay(millis)`** suspends the current [coroutine]({{ "/en/glossary/coroutines/" | relative_url }}) for a given time *without blocking* its [thread]({{ "/en/glossary/thread/" | relative_url }}): the dispatcher is free to run other work and resumes the coroutine when the time elapses. That is the difference from `Thread.sleep`, which parks the thread itself. `delay` is a [cancellable]({{ "/en/glossary/cooperative-cancellation/" | relative_url }}) [suspension point]({{ "/en/glossary/suspension-point/" | relative_url }}) — it throws [`CancellationException`]({{ "/en/glossary/cancellation-exception/" | relative_url }}) if the job is cancelled while waiting.

```kotlin
// Not found in FAS — standalone example
suspend fun retry(times: Int, block: suspend () -> Unit) {
    repeat(times) { attempt ->
        runCatching { block() }.onSuccess { return }
        delay(1000L * (attempt + 1))   // backoff: suspends, never blocks
    }
}
```

## The Senior Nuance

- **In tests, `delay` is virtual time.** Under [`runTest`]({{ "/en/glossary/run-test/" | relative_url }}) the [`TestDispatcher`]({{ "/en/glossary/test-dispatcher/" | relative_url }}) skips it instantly, so a one-hour backoff costs microseconds. That is why a real `delay` in a test is fine and a `Thread.sleep` is a bug.
- **Never use `delay` to "wait for" another coroutine.** It makes tests flaky and code racy; use `join()`, `await()` or `advanceUntilIdle()`. If a test only passes with a `delay`, it is hiding a synchronisation problem — a common symptom after adding a [`flowOn`]({{ "/en/glossary/flow-on/" | relative_url }}) and its [buffer]({{ "/en/glossary/buffer/" | relative_url }}).
- **It is a cancellation checkpoint.** A loop with a `delay` is automatically cooperative; a tight CPU loop without one needs an explicit `ensureActive()`.
