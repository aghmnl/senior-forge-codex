## The Theory (The What)

**Upstream** is everything that comes *before* a given point in a [`Flow`]({{ "/en/glossary/flow/" | relative_url }}) chain: the builder that produces the values and every operator declared above. In `dao.stream().map { }.flowOn(IO).filter { }.collect { }`, the upstream of `flowOn` is `dao.stream()` plus the `map`. The word matters because the operators that change context or buffer — [withContext vs flowOn]({{ "/en/02-coroutines-flow/with-context-vs-flow-on/" | relative_url }})'s `flowOn`, `buffer`, `conflate` — affect **only** their upstream, never what comes after.

```kotlin
// Not found in FAS — standalone example
readFilesFlow()            // ── upstream of flowOn
    .map { it.parse() }    // ── upstream of flowOn
    .flowOn(Dispatchers.IO)
    .filter { it.isValid } // ── downstream: runs in the collector's context
    .collect { render(it) }
```

## The Senior Nuance

- **Upstream is a position, not a type.** The same operator is upstream of what follows it and [downstream]({{ "/en/glossary/downstream/" | relative_url }}) of what precedes it; `flowOn` splits the chain at the exact spot where you write it.
- **Exceptions flow downstream, values flow downstream, context flows upstream.** That inversion is the single most confusing thing about `flowOn` and the reason `.catch { }` also only sees failures from *its* upstream.
- **Put `flowOn` as close to the producer as possible.** Anything between the producer and the `flowOn` inherits the dispatcher; operators you want on the collector's context belong after it.
- See [withContext vs flowOn]({{ "/en/02-coroutines-flow/with-context-vs-flow-on/" | relative_url }}).
