## The Theory (The What)

**`retry(n)`** and **`retryWhen { cause, attempt -> }`** are [upstream]({{ "/en/glossary/upstream/" | relative_url }}) operators that resubscribe to the [flow]({{ "/en/glossary/flow/" | relative_url }}) when it fails: the producer runs again from the beginning, up to `n` times or while the predicate returns `true`. They sit *above* a [`catch`]({{ "/en/glossary/catch/" | relative_url }}) in the chain — retry first, and only give up to `catch` when the attempts are exhausted. `retryWhen` is the one worth knowing, because it receives the cause and the attempt index, so you can back off and filter by exception type.

```kotlin
// Not found in FAS — standalone example
remoteTasks()
    .retryWhen { cause, attempt ->
        val transient = cause is IOException && attempt < 3
        if (transient) delay(1000L * (attempt + 1))   // exponential-ish backoff
        transient                                     // true = retry, false = give up
    }
    .catch { emit(emptyList()) }
    .collect { render(it) }
```

## The Senior Nuance

- **Retry only what is transient.** An `IOException` may succeed on a second attempt; a parsing error or a 4xx will fail identically forever, and retrying it just burns battery and delays the error the user needs to see.
- **Always back off, never spin.** `retry(3)` with no [`delay`]({{ "/en/glossary/delay/" | relative_url }}) hammers the server three times in microseconds. A growing delay is the difference between a retry and an accidental denial-of-service against your own backend.
- **Order matters: retry above, catch below.** `catch` placed above `retryWhen` would consume the failure before the retry ever sees it.
