## The Theory (The What)

A **lock** protects a piece of code so that **only one thread can run it at a time**. A thread that wants to enter while another is inside has to wait until the lock is released. In Kotlin on the JVM the usual forms are the [synchronized]({{ "/en/glossary/synchronized-block/" | relative_url }}) block and `ReentrantLock`; in coroutines, `Mutex` plays the same role but **suspends** the coroutine instead of blocking the [thread]({{ "/en/glossary/thread/" | relative_url }}).

```kotlin
// Not found in FAS — standalone example
private val mutex = Mutex()
private var cache: Map<String, Task> = emptyMap()

suspend fun refresh() {
    mutex.withLock {           // only one coroutine at a time in here
        cache = api.fetchTasks().associateBy { it.id }
    }
}
```

## The Senior Nuance

- **A lock makes others wait; compare-and-set makes the loser retry.** [update {}]({{ "/en/glossary/update/" | relative_url }}) uses no lock: nobody waits, and whoever loses the race recomputes. That is why it is cheap for small, fast state changes.
- **Never block a thread inside a coroutine.** A `synchronized` block that waits blocks the whole thread, including the [main thread]({{ "/en/glossary/main-thread/" | relative_url }}) if that is where it runs. In coroutines, use `Mutex`, which suspends.
- **Locks can deadlock.** Two pieces of code that each hold one lock and wait for the other's lock wait forever. Keeping the protected section short, and never calling unknown code inside it, avoids most cases.
