## The Theory (El Qué)

Un **Map** en Kotlin es una colección de pares clave-valor donde cada clave es única. La biblioteca estándar provee `Map<K, V>` (solo lectura) y `MutableMap<K, V>` (modificable). Las implementaciones comunes incluyen `HashMap`, `LinkedHashMap` y `sortedMapOf`. Las funciones de fábrica como `mapOf()` y `mutableMapOf()` crean instancias de forma concisa.

```kotlin
// De FollowApp Suite — PresetMapper.kt
fun deserializeLabelFilters(json: String): Map<String, LabelFilterState> {
    if (json.isBlank() || json == "{}") return emptyMap()
    val obj = JSONObject(json)
    val result = mutableMapOf<String, LabelFilterState>()
    obj.keys().forEach { key ->
        runCatching { LabelFilterState.valueOf(obj.getString(key)) }
            .onSuccess { result[key] = it }
    }
    return result
}
```

## The Senior Nuance (El Matiz Senior)

- Kotlin separa la interfaz de solo lectura `Map` de `MutableMap`. Retornar `Map` desde una función señala que los llamadores no deberían [mutar]({{ "/es/glosario/mutation/" | relative_url }}) la colección — aunque la instancia subyacente puede seguir siendo mutable. Es una señal de intención, no una garantía en tiempo de compilación.
- Cuando se usa una `data class` como clave de un map, solo las propiedades del [constructor primario]({{ "/es/glosario/primary-constructor/" | relative_url }}) participan en `hashCode()` y `equals()`. Si una propiedad del cuerpo cambia entre inserciones, el map encuentra la entrada igualmente — pero si cambia una propiedad del constructor (vía un `var` mutable), la entrada se vuelve inalcanzable. Preferí claves inmutables.
- `mapOf("a" to 1)` usa la función infix `to`, que crea un `Pair`. Para maps grandes, `buildMap { put("a", 1) }` evita allocations intermedios de `Pair`.
