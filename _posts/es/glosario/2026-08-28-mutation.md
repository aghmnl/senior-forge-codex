## The Theory (El Qué)

**Mutation** (mutación) significa cambiar el estado de un objeto después de que fue creado. En Kotlin, `var` declara una variable mutable (reasignable), mientras que `val` declara una referencia de solo lectura. Para colecciones, `MutableList`, `MutableMap` y `MutableSet` exponen operaciones de mutación (`add`, `remove`, `put`), mientras que sus contrapartes de solo lectura (`List`, `Map`, `Set`) no lo hacen.

```kotlin
// De FollowApp Suite — PresetMapper.kt
// Patrón construir-luego-exponer: mutar localmente, retornar inmutable
val result = mutableMapOf<String, LabelFilterState>()
obj.keys().forEach { key ->
    runCatching { LabelFilterState.valueOf(obj.getString(key)) }
        .onSuccess { result[key] = it }
}
return result  // retornado como Map — los llamadores ven solo lectura
```

## The Senior Nuance (El Matiz Senior)

- Las colecciones de solo lectura de Kotlin no son verdaderamente inmutables — son interfaces que ocultan los métodos de mutación, pero la instancia subyacente puede castearse a su contraparte mutable. Para inmutabilidad estructural, usá `kotlinx.collections.immutable` (`persistentListOf`, `persistentMapOf`).
- En arquitecturas de [flujo unidireccional]({{ "/es/glosario/unidirectional-data-flow/" | relative_url }}), evitar la mutación es la base: en vez de modificar el estado en el lugar, se crea un nuevo objeto de estado vía `copy()`. Esto hace que las [transiciones de estado]({{ "/es/glosario/state-transitions/" | relative_url }}) sean explícitas, rastreables y thread-safe.
- El patrón "construir mutable, exponer inmutable" (como en el ejemplo FAS) es Kotlin idiomático: usá un `MutableMap` internamente durante la construcción, luego retornalo como `Map`. Las funciones `buildMap {}`, `buildList {}` y `buildSet {}` formalizan este patrón.
