## The Theory (El Qué)

**Dagger** es un framework de inyección de dependencias totalmente estático, en [compile time]({{ "/es/glosario/compile-time/" | relative_url }}), para Java y Kotlin. Genera todo el código de wiring en compile time vía [annotation processing]({{ "/es/glosario/annotation-processing/" | relative_url }}), produciendo un [dependency graph]({{ "/es/glosario/dependency-graph/" | relative_url }}) que la [JVM]({{ "/es/glosario/jvm/" | relative_url }}) puede ejecutar con cero overhead de [runtime reflection]({{ "/es/glosario/runtime-reflection/" | relative_url }}). [Hilt]({{ "/es/glosario/hilt/" | relative_url }}) está construido sobre Dagger y provee convenciones específicas de Android (componentes, scopes y entry points predefinidos) que eliminan la mayor parte del boilerplate de Dagger.

```kotlin
// From FollowApp Suite — DatabaseModule.kt
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {

    @Provides
    @Singleton
    fun provideMyTasksDatabase(
        @ApplicationContext context: Context
    ): MyTasksDatabase {
        return Room.databaseBuilder(
            context,
            MyTasksDatabase::class.java,
            "mytasks_database.db"
        )
            .addMigrations(MIGRATION_1_2)
            .build()
    }

    @Provides
    @Singleton
    fun provideTaskDao(database: MyTasksDatabase): TaskDao = database.taskDao()
}
```

`@Module` + `@Provides` le dice a Dagger cómo crear cada dependencia; `@InstallIn(SingletonComponent::class)` la scopea al lifetime de la app.

## The Senior Nuance (El Matiz Senior)

- **Dagger vs [Hilt]({{ "/es/glosario/hilt/" | relative_url }})**: Hilt es Dagger con opiniones. Predefine jerarquías de componentes (`SingletonComponent`, `ActivityComponent`, `ViewModelComponent`) para que no tengas que wirearlos vos. Los desarrolladores senior usan Hilt para proyectos Android y Dagger puro solo para módulos no-Android o librerías multiplataforma.
- **Seguridad en compile time**: A diferencia de patrones service-locator (Koin), Dagger detecta bindings faltantes en compile time. Si una dependencia no está provista, el build falla — nunca descubrís un binding faltante en [runtime]({{ "/es/glosario/runtime/" | relative_url }}).
- **`@Inject` constructor vs field injection**: La inyección por [constructor]({{ "/es/glosario/constructor/" | relative_url }}) es preferible porque hace las dependencias explícitas y habilita inmutabilidad (`val`). La field injection (`lateinit var` + `@Inject`) se reserva para entry points de Android (`Activity`, `Fragment`, `Service`) donde el framework controla la [construcción]({{ "/es/glosario/constructor/" | relative_url }}).
- **Costo de build time**: El [annotation processing]({{ "/es/glosario/annotation-processing/" | relative_url }}) de Dagger agrega tiempo al build, especialmente en proyectos grandes con muchos módulos. El soporte de KSP (Kotlin Symbol Processing) está mejorando esto, pero sigue siendo un trade-off que los desarrolladores senior consideran al elegir un framework de DI.
- **Testing**: Los módulos de Dagger/Hilt se pueden reemplazar en tests con `@TestInstallIn` o `@UninstallModules`, permitiendo intercambiar implementaciones reales por fakes sin cambiar código de producción.
