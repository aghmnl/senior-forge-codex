## The Theory (El Qué)

En Kotlin, las clases y funciones son **final por defecto** — no se pueden heredar ni sobreescribir a menos que estén marcadas explícitamente como `open` o `abstract`. Esto es lo opuesto a Java, donde todo es open por defecto y hay que marcar `final` para prevenir la extensión.

```kotlin
// Not found in FAS — standalone example
class PaymentProcessor {                       // final — no se puede subclasificar
    fun validate(amount: Double): Boolean = amount > 0  // final — no se puede sobreescribir
}

open class BaseRepository {                    // open — se permite la herencia
    open fun findAll(): List<Any> = emptyList() // open — se permite el override
    fun count(): Int = findAll().size            // final — no se puede sobreescribir
}
```

A nivel de [JVM]({{ "/es/glosario/jvm/" | relative_url }}), los métodos `final` habilitan la **devirtualización**: el [JIT compiler]({{ "/es/glosario/jit-compiler/" | relative_url }}) sabe que ninguna subclase puede sobreescribirlos, así que puede saltear la [vtable]({{ "/es/glosario/vtable/" | relative_url }}) e inlinear el método directamente — convirtiendo un [virtual dispatch]({{ "/es/glosario/virtual-dispatch/" | relative_url }}) en un [static dispatch]({{ "/es/glosario/static-dispatch/" | relative_url }}).

## The Senior Nuance (El Matiz Senior)

- El final-by-default de Kotlin es una decisión de diseño deliberada siguiendo "Effective Java" Item 19: *Diseñá y documentá para herencia o prohibila*. Obligar a los desarrolladores a optar por la apertura fuerza decisiones conscientes sobre qué puntos de extensión soportar.
- Final-by-default genera fricción con frameworks que dependen de proxies de subclases — [Mockito]({{ "/es/glosario/mockito/" | relative_url }}) no puede mockear clases final sin la extensión `mockito-inline`, y Hibernate necesita el plugin de compilador `kotlin-allopen` para generar proxies de entidades. Los desarrolladores senior conocen estos workarounds.
- Las [data classes]({{ "/es/01-kotlin-core/data-classes/" | relative_url }}) son implícitamente final y no se pueden hacer `open`. Esto es intencional: el contrato de `equals`/`hashCode` se rompería con herencia (una violación clásica del Principio de Sustitución de Liskov).
- Las [sealed classes]({{ "/es/01-kotlin-core/sealed-classes-interfaces/" | relative_url }}) invierten el patrón: la jerarquía es abierta *dentro de su módulo* pero cerrada al mundo exterior. Esto habilita el chequeo de [exhaustividad]({{ "/es/glosario/exhaustiveness/" | relative_url }}) en expresiones `when` mientras se permite el subtipado controlado.
- En paths críticos de performance, `final` importa: el [JIT compiler]({{ "/es/glosario/jit-compiler/" | relative_url }}) de la JVM puede devirtualizar e inlinear métodos final, eliminando lookups de [vtable]({{ "/es/glosario/vtable/" | relative_url }}) por completo. Kotlin te da esta optimización por defecto.
