## The Theory (El Qué)

**Hilt** es el framework de inyección de dependencias (DI) recomendado para Android, construido sobre Dagger 2. Usa [annotation processing]({{ "/es/glosario/annotation-processing/" | relative_url }}) para generar el [grafo de dependencias]({{ "/es/glosario/dependency-graph/" | relative_url }}) en [compile time]({{ "/es/glosario/compile-time/" | relative_url }}), proveyendo DI type-safe y sin reflection con scopes predefinidos para componentes Android (`@Singleton`, `@ViewModelScoped`, `@ActivityScoped`, etc.).

El sistema de módulos de Hilt usa patrones de [funciones de orden superior]({{ "/es/01-kotlin-core/higher-order-functions-lambdas/" | relative_url }}) bajo el capó: los métodos `@Provides` actúan como funciones factory, y `@Binds` declara mappings de interfaz a implementación que el código generado resuelve estáticamente.

```kotlin
// Not found in FAS — standalone example
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    abstract fun bindTaskRepository(impl: TaskRepositoryImpl): TaskRepository
}

@Module
@InstallIn(ViewModelComponent::class)
object UseCaseModule {
    @Provides
    @ViewModelScoped
    fun provideGetTasksUseCase(repo: TaskRepository): GetTasksUseCase =
        GetTasksUseCase(repo)
}
```

## The Senior Nuance (El Matiz Senior)

- Hilt genera todo el wiring de DI en [compile time]({{ "/es/glosario/compile-time/" | relative_url }}) vía [annotation processing]({{ "/es/glosario/annotation-processing/" | relative_url }}) (KSP o KAPT). Esto significa que los errores de DI se capturan durante el build, no en [Runtime]({{ "/es/glosario/runtime/" | relative_url }}) — a diferencia de patrones de service-locator como Koin, que fallan en runtime cuando falta una dependencia.
- El [DSL]({{ "/es/glosario/dsl/" | relative_url }}) con scopes de Hilt (`@InstallIn(SingletonComponent::class)`, `@InstallIn(ViewModelComponent::class)`) mapea directamente a scopes del lifecycle de Android. Una dependencia `@ViewModelScoped` vive mientras vive el ViewModel, y luego es recolectada por el GC — este alineamiento automático con el lifecycle previene [memory leaks]({{ "/es/glosario/memory-leaks/" | relative_url }}).
- `@HiltViewModel` + `@Inject constructor` es el patrón estándar para inyectar dependencias en ViewModels. Hilt crea el ViewModel vía `ViewModelProvider.Factory` automáticamente — sin necesidad de factory manual.
- En proyectos multi-módulo, el `@InstallIn` de Hilt asegura que cada feature module contribuye al grafo global sin acoplamiento. Esta es una ventaja arquitectónica clave para apps Android grandes con dynamic feature modules.
- El trade-off es el tiempo de build: el annotation processing de Hilt agrega segundos a builds incrementales, especialmente con KAPT. Migrar a KSP reduce esto significativamente. Los desarrolladores senior evalúan este costo contra la seguridad del DI en compile-time.
