## The Theory (El Qué)

En el contexto de [procesamiento de anotaciones]({{ "/es/glosario/annotation-processing/" | relative_url }}), los **stubs** son archivos fuente Java simplificados generados a partir de código Kotlin por [kapt]({{ "/es/glosario/kapt/" | relative_url }}). Como los procesadores de anotaciones Java solo entienden código fuente Java, kapt debe traducir cada archivo Kotlin a un stub Java — un esqueleto con la estructura de clase correcta, firmas de métodos y anotaciones, pero sin cuerpos de implementación. Estos stubs luego se alimentan a la API `javax.annotation.processing` de Java.

## The Senior Nuance (El Matiz Senior)

- **Los stubs son la razón de que kapt sea lento**: Generar un stub Java por cada archivo fuente Kotlin es un paso costoso de [compile time]({{ "/es/glosario/compile-time/" | relative_url }}). En codebases grandes, la generación de stubs sola puede tomar más tiempo que el procesamiento de anotaciones en sí — es la motivación principal para migrar a [KSP]({{ "/es/glosario/ksp/" | relative_url }}), que elimina los stubs por completo.
- **Los stubs son lossy**: Features de Kotlin como `suspend`, parámetros default, `value class` y anotaciones de nullability no pueden representarse perfectamente en stubs Java. Esto significa que los procesadores basados en kapt pueden ver una imagen incompleta del código Kotlin.
- **No es lo mismo que test stubs**: En testing, "stub" significa una implementación fake que retorna valores predeterminados. En procesamiento de anotaciones, "stub" es específicamente el esqueleto Java generado. El contexto determina el significado.
- **KSP resuelve el problema**: [KSP]({{ "/es/glosario/ksp/" | relative_url }}) lee símbolos del compilador Kotlin directamente, así que no se necesita traducción a Java. El procesador ve código Kotlin como Kotlin — con información completa de nullability, suspend y extension preservada.
