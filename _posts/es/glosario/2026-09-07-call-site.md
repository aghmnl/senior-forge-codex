## The Theory (El Qué)

El **call site** (sitio de llamada) es el lugar exacto del [Source Code]({{ "/es/glosario/source-code/" | relative_url }}) donde una función es invocada — en oposición al *declaration site* (sitio de declaración), donde se define. La distinción importa porque varias características de Kotlin se comportan distinto según de qué lado de esa línea esté trabajando el compilador.

```kotlin
// From FollowApp Suite — SelectableListScaffold.kt
// DECLARATION SITE: acá T es un placeholder desconocido.
fun <T> SelectableListScaffold(
    items: List<T>,
    itemKey: (T) -> String,
    // ...
) { /* ... */ }
```

```kotlin
// From FollowApp Suite — TrashScreen.kt
// CALL SITE: acá T se resuelve a un tipo concreto.
SelectableListScaffold(
    items = uiState.visibleTasks,   // T se infiere de este argumento
    itemKey = { it.id },
    // ...
)
```

En el declaration site el compilador solo conoce las restricciones sobre `T` (su [Upper Bound]({{ "/es/glosario/upper-bound/" | relative_url }})). En el call site conoce el tipo real, porque el [Type Inference]({{ "/es/glosario/type-inference/" | relative_url }}) lo resolvió a partir de los argumentos.

## The Senior Nuance (El Matiz Senior)

- **Las [Inline Functions]({{ "/es/glosario/inline-functions/" | relative_url }}) se copian dentro del call site.** El compilador no emite una invocación de método normal; pega el cuerpo de la función donde se escribió la llamada. Ese es el mecanismo que hace posible [`reified`]({{ "/es/glosario/reified/" | relative_url }}) — el type argument concreto se conoce en el call site, así que puede quedar horneado en el [Bytecode]({{ "/es/glosario/bytecode/" | relative_url }}) ahí mismo. Es también el origen del [Code Bloat]({{ "/es/glosario/code-bloat/" | relative_url }}): una `inline` grande usada en cincuenta lugares produce cincuenta copias.
- **Varianza en el sitio de declaración vs de uso.** Kotlin te deja declarar la [Varianza]({{ "/es/glosario/variance/" | relative_url }}) una sola vez en la clase (`interface Producer<out T>`), y cada call site hereda esa promesa. Java no tiene esa opción: sus wildcards (`List<? extends T>`) son varianza *de sitio de uso*, repetida en cada call site. Es una de las ventajas ergonómicas concretas del sistema de tipos de Kotlin.
- **Non-local returns.** Dentro de la [Lambda]({{ "/es/glosario/lambdas/" | relative_url }}) de una [Inline Function]({{ "/es/glosario/inline-functions/" | relative_url }}), un `return` pelado sale de la función *envolvente* en el call site, no solo de la lambda — precisamente porque el cuerpo de la lambda se compila dentro de ese call site. [`crossinline`]({{ "/es/glosario/crossinline/" | relative_url }}) es lo que lo prohíbe cuando la lambda se va a ejecutar en otro lado.
- **Diagnosticar generics empieza en el call site.** Cuando una API genérica no compila, el error se reporta en el call site pero está *causado* por la declaración — un `out` faltante, o un type parameter usado en posición *in* y *out* a la vez. Leé las posiciones de la declaración antes de reescribir la llamada.
