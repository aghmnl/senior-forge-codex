## The Theory (El Qué)

Una **Subclase** es una clase que deriva de otra (su *superclase* o padre), heredando sus miembros y opcionalmente especializándolos con `override`. La subclase es un *subtipo*: cualquier referencia al padre puede contener una instancia de la subclase, y eso es lo que hace posible el [Polymorphism]({{ "/es/glosario/polymorphism/" | relative_url }}).

En Kotlin, las clases son [`final`]({{ "/es/glosario/final/" | relative_url }}) por defecto. Para poder subclasear, el padre tiene que optar con `open`:

```kotlin
// From FollowApp Suite — TrashPreferences.kt
@Singleton
open class TrashPreferences @Inject constructor(
    private val dataStore: DataStore<Preferences>
) {
    open fun skipDeleteConfirmation(): Flow<Boolean> = dataStore.data.map { prefs ->
        prefs[skipDeleteConfirmKey] ?: false
    }
}
```

Una [Sealed Hierarchy]({{ "/es/glosario/sealed-hierarchy/" | relative_url }}) es la forma restringida: el conjunto de subclases es fijo y conocido por el compilador.

```kotlin
// From FollowApp Suite — StateChip.kt
sealed interface ChipState {
    val foreground: Color @Composable get
    @Composable fun inputColors(): SelectableChipColors
}

object Full : ChipState {
    override val foreground: Color
        @Composable get() = MaterialTheme.colorScheme.onPrimaryContainer

    @Composable
    override fun inputColors(): SelectableChipColors = /* ... */
}
```

## The Senior Nuance (El Matiz Senior)

- **`open` es una decisión de diseño, y muchas veces de testing.** `TrashPreferences` es `open` no porque algo la extienda en producción, sino para que los tests puedan sustituirla por un fake. Un Senior nota que abrir una clase por mockeabilidad es un olor que una interfaz resolvería con más honestidad — y que librerías como MockK pueden mockear clases [`final`]({{ "/es/glosario/final/" | relative_url }}) igual.
- **Subclasear es el acoplamiento más fuerte disponible.** Una subclase depende de la implementación del padre, no solo de su contrato, así que un cambio en el padre cambia silenciosamente cada subclase. Es el problema de la fragile base class, y es la razón por la que Kotlin hizo [`final`]({{ "/es/glosario/final/" | relative_url }}) el default.
- **Las subclases [`final`]({{ "/es/glosario/final/" | relative_url }}) son más rápidas.** Cuando un método no puede sobreescribirse, el [JIT Compiler]({{ "/es/glosario/jit-compilation/" | relative_url }}) puede desvirtualizarlo — convirtiendo el [Virtual Dispatch]({{ "/es/glosario/virtual-dispatch/" | relative_url }}) por [vtable]({{ "/es/glosario/vtable/" | relative_url }}) en [Static Dispatch]({{ "/es/glosario/static-dispatch/" | relative_url }}), y muchas veces inlineándolo directamente.
- **Subclase ≠ subtipo en el caso genérico.** `Dog` es subtipo de `Animal`, pero `Box<Dog>` *no* es subtipo de `Box<Any>` salvo que la clase declare [Covarianza]({{ "/es/glosario/covariance/" | relative_url }}) con `out`. Confundir ambas cosas es uno de los errores más comunes con generics.
- **Preferí composición y delegación.** El [`by`]({{ "/es/glosario/by-delegation/" | relative_url }}) de Kotlin te da reutilización de interfaces sin el acoplamiento de la [Inheritance]({{ "/es/glosario/inheritance/" | relative_url }}) — la razón por la que existe como [Keyword]({{ "/es/glosario/keyword/" | relative_url }}) de primera clase.
