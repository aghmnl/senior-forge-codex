## The Theory (El Qué)

`MutableStateFlow.update {}` aplica una transformación al valor actual de forma **atómica**. Lee el valor, ejecuta tu lambda y publica el resultado solo si nada cambió en el medio — reintentando con el valor fresco en caso contrario. Es la forma correcta de expresar "estado nuevo = f(estado viejo)".

```kotlin
// De FollowApp Suite — TasksViewModel.kt
fun onTaskSelectionToggled(taskId: String) {
    _uiState.update {
        val updated = if (taskId in it.selectedTaskIds) {
            it.selectedTaskIds - taskId
        } else {
            it.selectedTaskIds + taskId
        }
        it.copy(selectedTaskIds = updated)
    }
}
```

## The Senior Nuance (El Matiz Senior)

- La regla es mecánica: **si el valor nuevo menciona al valor viejo, usá `update`; si no lo menciona, `value =` está bien.** `_uiState.value = TasksUiState()` es una publicación directa. `_uiState.value = _uiState.value.copy(...)` es una [Race Condition]({{ "/es/glosario/race-condition/" | relative_url }}) esperando un frame lento.
- La lambda puede correr varias veces por el reintento de [Compare-and-Set]({{ "/es/glosario/compare-and-set/" | relative_url }}), así que debe ser **pura**: nada de logging, analytics, navegación ni llamadas a repositorios. Calculá el estado siguiente, devolvelo, y hacé los side effects después.
- `update` compone para estado anidado sin romper la [Atomicity]({{ "/es/glosario/atomicity/" | relative_url }}), porque el [`copy`]({{ "/es/glosario/copy/" | relative_url }}) anidado ocurre dentro del bloque: `_uiState.update { it.copy(form = it.form.copy(title = title)) }`. Leer `_uiState.value.form` *fuera* del bloque y pasarlo adentro reintroduce la race que estabas evitando.
