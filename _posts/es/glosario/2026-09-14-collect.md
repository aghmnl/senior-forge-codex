## The Theory (El Qué)

**`collect { }`** es la [suspend function]({{ "/es/glosario/suspend-functions/" | relative_url }}) terminal de un [`Flow`]({{ "/es/glosario/flow/" | relative_url }}): arranca el flow, recibe cada valor emitido en la lambda, y no devuelve hasta que el flow completa — lo que para un `StateFlow` o un flow de query de Room es nunca. Por eso tiene que correr dentro de una coroutine cuyo [lifecycle]({{ "/es/glosario/lifecycle/" | relative_url }}) la acote.

```kotlin
// From FollowApp Suite — PremiumRepositoryImpl.kt
scope.launch {
    billingConnector.isOwned
        .filterNotNull()
        .collect { owned -> premiumPreferences.setAdsRemoved(owned) }
}
```

## The Senior Nuance (El Matiz Senior)

- **`collect` suspende para siempre en flows calientes.** Lo que esté escrito después en la misma coroutine nunca corre. Dos flows necesitan dos `launch`, o `combine`.
- **Corre en el dispatcher del collector.** Los operadores upstream también, salvo que `flowOn` los mueva; la lambda siempre corre donde se llamó `collect`.
- **Una excepción en la lambda cancela la colección** y se propaga a la coroutine — con un [`SupervisorJob`]({{ "/es/glosario/supervisor-job/" | relative_url }}) y sin [`CoroutineExceptionHandler`]({{ "/es/glosario/coroutine-exception-handler/" | relative_url }}), eso es un crash. `catch { }` upstream maneja errores del emisor, no del collector.
- **En UI, preferí `collectAsStateWithLifecycle()` o `repeatOnLifecycle`** sobre un `collect` crudo en `lifecycleScope`, así la colección se detiene cuando la pantalla no está visible.
