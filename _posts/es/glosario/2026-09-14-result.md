## The Theory (El Qué)

**`kotlin.Result<T>`** es el tipo de la standard library que contiene o bien un valor de éxito o bien un `Throwable`. `runCatching { }` produce uno; `getOrNull()`, `getOrDefault()`, `getOrThrow()`, `onSuccess { }`, `onFailure { }`, `map { }` y `fold(...)` lo consumen. Convierte una excepción en un valor que el llamador tiene que mirar, en vez de uno que desenrolla la pila.

```kotlin
// From FollowApp Suite — BackupManager.kt
suspend fun exportTo(uri: Uri): Result<Unit> = withContext(Dispatchers.IO) {
    runCatching {
        // ... escritura del archivo
    }.onSuccess {
        Log.d(TAG, "Backup exported")
    }.onFailure { Log.e(TAG, "Backup export failed", it) }
}
```

El [return type]({{ "/es/glosario/return-type/" | relative_url }}) `Result<Unit>` le dice al ViewModel que exportar puede fallar de formas esperadas que debe presentar, no crashear.

## The Senior Nuance (El Matiz Senior)

- **`runCatching` atrapa todo — incluida [`CancellationException`]({{ "/es/glosario/cancellation-exception/" | relative_url }}).** En una coroutine eso convierte un scope cancelado en uno que sigue trabajando. Relanzala: `.onFailure { if (it is CancellationException) throw it }`, o atrapá tipos específicos con un [`try/catch`]({{ "/es/glosario/try-catch/" | relative_url }}) común.
- **Usalo para fallos esperados, no para bugs.** "No se pudo abrir el archivo" es un `Result`; una `NullPointerException` por una [invariante]({{ "/es/glosario/invariant/" | relative_url }}) rota debería crashear fuerte.
- **Una sealed hierarchy suele ser mejor para errores de dominio** — `Result` solo lleva un `Throwable`, así que los llamadores tienen que hacer `is` sobre clases de excepción para ramificar. Una `sealed interface ExportError` documenta los casos.
- Es una value class sobre `Any?`: barata, pero históricamente restringida como return type directo (levantado en Kotlin 1.5).
