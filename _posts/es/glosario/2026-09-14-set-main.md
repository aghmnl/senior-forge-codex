## The Theory (El Qué)

**`Dispatchers.setMain(dispatcher)`** (de `kotlinx-coroutines-test`) reemplaza el [`Dispatchers.Main`]({{ "/es/glosario/dispatchers-main/" | relative_url }}) global durante un test unitario de JVM, donde no existe ningún [`Looper`]({{ "/es/glosario/looper/" | relative_url }}) de Android. Todo lo que usa `Main` — [`viewModelScope`]({{ "/es/glosario/viewmodel-scope/" | relative_url }}), `Main.immediate`, `lifecycleScope` — pasa a correr en el [`TestDispatcher`]({{ "/es/glosario/test-dispatcher/" | relative_url }}) provisto. `resetMain()` restaura el original.

```kotlin
// From FollowApp Suite — SettingsViewModelTest.kt
@Before
fun setup() {
    Dispatchers.setMain(testDispatcher)
}

@After
fun tearDown() {
    Dispatchers.resetMain()
}
```

## The Senior Nuance (El Matiz Senior)

- **Es estado global del proceso.** Olvidar `resetMain()` filtra el dispatcher de test a la próxima clase de test. Emparejalos en `@Before`/`@After`, o usá una JUnit rule que haga ambas cosas.
- **Solo alcanza a `Main`.** Un `withContext(Dispatchers.IO)` dentro de la clase bajo test sigue saltando a un thread real que el test no controla. Ese hueco es el que cierra la inyección de dispatchers ([`@IoDispatcher`]({{ "/es/glosario/io-dispatcher/" | relative_url }})).
- **Sin él, `Dispatchers.Main` lanza una excepción** ("Module with the Main dispatcher is missing") la primera vez que un ViewModel hace launch en un test de JVM puro.
