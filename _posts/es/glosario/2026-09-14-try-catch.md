## The Theory (El Qué)

**`try { } catch (e: T) { } finally { }`** es el manejo estructurado de excepciones de Kotlin. `try` es una *expresión* — produce el valor de la última línea del bloque que corrió — y `finally` siempre se ejecuta, incluso en la cancelación. Atrapar por tipo es todo el diseño: atrapá las excepciones que podés manejar, dejá que el resto se propague.

```kotlin
// From FollowApp Suite — SettingsViewModel.kt
viewModelScope.launch {
    try {
        val session = googleAuthClient.signIn(activityContext)
        saveUserSessionUseCase(session)
    } catch (e: GetCredentialCancellationException) {
        Log.d(TAG, "Google sign-in cancelled by user")
    } catch (e: GetCredentialException) {
        _uiState.update { it.copy(messageRes = R.string.error_sign_in) }
    }
}
```

Dos cláusulas `catch`, dos decisiones: la cancelación del usuario no es un error; un fallo real se convierte en estado de UI.

## The Senior Nuance (El Matiz Senior)

- **`catch (e: Exception)` en una coroutine se traga [`CancellationException`]({{ "/es/glosario/cancellation-exception/" | relative_url }}).** La coroutine entonces continúa después de que se le dijo que pare. Atrapá tipos específicos, o relanzá: `if (e is CancellationException) throw e`.
- **`finally` corre también en la cancelación.** Eso es lo que lo convierte en el lugar para el cleanup — y por eso el cleanup que a su vez suspende necesita `withContext(NonCancellable)`.
- **Kotlin no tiene checked exceptions.** Nada obliga a un llamador a atrapar; la firma no dice qué puede lanzarse. [`Result`]({{ "/es/glosario/result/" | relative_url }}) o un tipo de error sealed es como hacés visible el fallo en el tipo.
- **No atrapes para loguear y relanzar en cada capa.** Un handler en el límite que es dueño de la decisión; todo lo de abajo la deja propagar.
