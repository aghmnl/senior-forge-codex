## The Theory (El Qué)

Un **SDK** (*Software Development Kit*) es la librería más el tooling de un proveedor que integrás para usar su servicio — Google Mobile Ads, Firebase, Play Billing, un proveedor de pagos, analytics. En Android suele llegar como un AAR con un punto de entrada `initialize()`, una API basada en [callbacks]({{ "/es/glosario/callbacks/" | relative_url }}), y a veces un `ContentProvider` que se auto-arranca al lanzar el proceso. Desde el punto de vista de main-safety un SDK es *código opaco que corre en el thread desde el que lo llames*.

```kotlin
// From FollowApp Suite — ConsentManager.kt
// MobileAds.initialize does ~700 ms of synchronous SDK bootstrap on
// the caller thread even though it exposes an async callback.
CoroutineScope(SupervisorJob() + Dispatchers.IO).launch {
    MobileAds.initialize(app)
}
```

## The Senior Nuance (El Matiz Senior)

- **Un parámetro callback no significa que la llamada sea asíncrona.** `initialize(context, listener)` puede hacer cientos de milisegundos de trabajo síncrono antes de retornar y *después* llamar al listener. Medí con [profiling]({{ "/es/glosario/profiling/" | relative_url }}); no confíes en la firma.
- **La inicialización del SDK va fuera de Main y fuera del camino crítico del cold start.** [`Application.onCreate()`]({{ "/es/glosario/application-on-create/" | relative_url }}) es el peor lugar para eso; un dispatcher de fondo después del primer frame, o lazy en el primer uso, es el correcto.
- **Envolvé el SDK detrás de tu propia interfaz.** Aísla su modelo de threading, te deja inyectar un fake en tests, y convierte un futuro cambio de SDK en un cambio de un archivo.
