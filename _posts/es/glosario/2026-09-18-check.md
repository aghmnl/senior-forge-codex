## The Theory (El Qué)

**`check(condition) { "mensaje" }`** valida una *invariante del estado del objeto*: si la condición es falsa lanza `IllegalStateException`. Es el hermano de [`require`]({{ "/es/glosario/require/" | relative_url }}) — misma forma, distinta excepción, distinto significado: `require` dice que los argumentos del llamador están mal, `check` dice que el objeto mismo está en un estado en el que nunca debería estar. Como `require`, declara un [contract]({{ "/es/glosario/contract/" | relative_url }}), así que el compilador aplica un smart cast ([Smart Casts]({{ "/es/01-kotlin-core/smart-casts/" | relative_url }})) después: `check(connection is Open)` convierte a `connection` en `Open` para el resto de la función.

```kotlin
// Not found in FAS — standalone example
class BillingConnector {
    private var state: ConnectionState = ConnectionState.Idle

    fun launchPurchase(activity: Activity) {
        check(state is ConnectionState.Connected) { "launchPurchase llamado antes de connect(), state=$state" }
        // acá `state` está smart-casteado a Connected
        state.client.launchBillingFlow(activity, params())
    }
}
```

## The Senior Nuance (El Matiz Senior)

- **`check` reemplaza a `!!` sobre estado.** `check(x != null)` seguido de `x` a secas es la versión honesta de `x!!`: el mismo crash ante la violación, pero con un mensaje que nombra la [invariante]({{ "/es/glosario/invariant/" | relative_url }}) rota en vez de una [`NullPointerException`]({{ "/es/glosario/null-pointer-exception/" | relative_url }}) anónima.
- **Elegí la excepción según quién tiene la culpa.** Si un test choca con una `IllegalStateException`, el bug está dentro de la clase; una `IllegalArgumentException` apunta al llamador. Esa distinción vale más que el chequeo en sí.
- **`error("msg")` para la rama inalcanzable.** Cuando una rama de `when` debería ser imposible, `error()` (que lanza `IllegalStateException`) lo documenta mejor que un `else` silencioso.
