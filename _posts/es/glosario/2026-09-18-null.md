## The Theory (El Qué)

**`null`** es el literal que significa "sin valor". En Kotlin solo puede asignarse a tipos *nullable* — los que se escriben con `?` al final, como [`String?`]({{ "/es/glosario/string/" | relative_url }}) — y el compilador rechaza `val s: String = null` en [tiempo de compilación]({{ "/es/glosario/compile-time/" | relative_url }}). Esa única regla convierte la [`NullPointerException`]({{ "/es/glosario/null-pointer-exception/" | relative_url }}) de sorpresa en runtime en error de tipo, y hace de `null` una parte deliberada del contrato de una API: un `T?` dice "esto puede faltar legítimamente", un `T` dice "esto siempre está". Todo lo del artículo [Null Safety: Elvis & Safe Calls]({{ "/es/01-kotlin-core/null-safety-elvis-safe-calls/" | relative_url }}) — [`?.`]({{ "/es/glosario/safe-call/" | relative_url }}), [`?:`]({{ "/es/glosario/elvis-operator/" | relative_url }}), [`as?`]({{ "/es/glosario/as-safe-cast/" | relative_url }}) — existe para pasar un valor de `T?` a `T` de forma explícita.

```kotlin
// Not found in FAS — standalone example
val email: String = "a@b.c"      // nunca null: el compilador lo garantiza
val photoUrl: String? = null     // ausente de forma legítima

// val bad: String = null        // no compila
val length = photoUrl?.length ?: 0
```

## The Senior Nuance (El Matiz Senior)

- **`null` es dato, no error.** Modelalo donde la ausencia significa algo (foto opcional, preferencia sin setear) y prohibilo donde no (un ID, un email). Hacer todo nullable "por las dudas" le impone un chequeo de null a cada consumidor.
- **`null` tiene su propio tipo: `Nothing?`.** Por eso `null` puede asignarse a cualquier `T?` y por eso `listOf(null)` infiere `List<Nothing?>`.
- **Las fuentes de NPE que quedan están en los bordes.** [Platform types]({{ "/es/glosario/platform-types/" | relative_url }}) desde Java, `!!` y lecturas de `lateinit` antes de inicializar son donde `null` todavía crashea una app Kotlin; tratá esos límites explícitamente.
