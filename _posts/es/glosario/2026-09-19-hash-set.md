## The Theory (El Qué)

**`HashSet`** es la implementación de `Set` de la JVM respaldada por una tabla hash: `add`, `remove` y `contains` son O(1) amortizado porque ubica un elemento por su bucket de [`hashCode`]({{ "/es/glosario/hash-code/" | relative_url }}) y después confirma con [`equals`]({{ "/es/glosario/equals/" | relative_url }}). No guarda orden — `LinkedHashSet` (lo que devuelven realmente `setOf`/`mutableSetOf`) preserva el orden de inserción. Su comportamiento es la prueba práctica de la igualdad generada de una data class ([Data Classes: copy, equals, toString]({{ "/es/01-kotlin-core/data-classes/" | relative_url }})): dos instancias iguales según las propiedades del [constructor primario]({{ "/es/glosario/primary-constructor/" | relative_url }}) cuentan como un solo elemento.

```kotlin
// Not found in FAS — standalone example
data class TaskId(val value: String) { var lastSeen: Long = 0 }

val ids = hashSetOf(TaskId("a").apply { lastSeen = 1 })
ids.add(TaskId("a").apply { lastSeen = 2 })   // false: lastSeen está en el cuerpo, así que son iguales
ids.size                                       // 1
```

## The Senior Nuance (El Matiz Senior)

- **El set es tan correcto como el `hashCode` del elemento.** Mutar una propiedad que participa del hash *después* de insertar deja al elemento varado en el bucket equivocado: está en el set pero `contains` dice que no. Los elementos de un hash set deberían ser inmutables.
- **`setOf` no es un `HashSet`.** Los `setOf`/`mutableSetOf` de Kotlin devuelven `LinkedHashSet`, que mantiene el orden de inserción — un detalle a tener en cuenta cuando un test afirma sobre el orden de iteración.
- **Las data classes son el tipo de elemento natural.** `equals`/`hashCode` generados desde propiedades `val` es exactamente el contrato que un hash set necesita; las clases escritas a mano suelen equivocarlo.
