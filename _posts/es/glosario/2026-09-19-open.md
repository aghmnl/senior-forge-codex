## The Theory (El Qué)

**`open`** es el modificador que hace que una clase sea heredable o un miembro sobreescribible. Kotlin invierte el default de Java: toda clase y todo miembro es `final` salvo que se marque `open`, así que extender es algo explícito y deliberado. Una data class ([Data Classes: copy, equals, toString]({{ "/es/01-kotlin-core/data-classes/" | relative_url }})) **no puede** ser `open` — ni `abstract`, `sealed` o `inner` — porque sus [`equals`]({{ "/es/glosario/equals/" | relative_url }}), `hashCode` y [`copy`]({{ "/es/glosario/copy/" | relative_url }}) generados derivan de *su propio* [constructor primario]({{ "/es/glosario/primary-constructor/" | relative_url }}) y una subclase los rompería.

```kotlin
// Not found in FAS — standalone example
open class Repository(open val name: String) {      // heredable
    open fun load() { }                             // sobreescribible
}

class TaskRepository(name: String) : Repository(name) {
    override fun load() { }
}

// data class Admin(...) : User(...)   // no compila: una data class no puede ser open
```

## The Senior Nuance (El Matiz Senior)

- **`final` por defecto es una postura de diseño.** La herencia es un contrato que hay que mantener para siempre; Kotlin te obliga a declarar esa intención. Preferí composición o una interfaz, y usá `open` cuando el polimorfismo es genuinamente el diseño.
- **`open` también afecta el razonamiento del compilador.** Un `open val` puede ser sobreescrito por una subclase con [getter]({{ "/es/glosario/getter/" | relative_url }}) custom, así que no es estable y no recibe [smart cast]({{ "/es/01-kotlin-core/smart-casts/" | relative_url }}).
- **Las librerías de mocking no son motivo para abrir una clase.** Dependé de interfaces, o usá un fake solo para tests; los workarounds con `allopen`/`mockk` filtran preocupaciones de testing al diseño de producción.
