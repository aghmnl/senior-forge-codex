## The Theory (El Qué)

**`toString`** produce la representación textual de un objeto: `Any.toString` devuelve `NombreClase@1a2b3c` (el tipo más un hash de identidad), que no le dice nada a quien lo lee. Una data class ([Data Classes: copy, equals, toString]({{ "/es/01-kotlin-core/data-classes/" | relative_url }})) lo sobreescribe con `User(id=7, name=Ada)` — todas las propiedades del [constructor primario]({{ "/es/glosario/primary-constructor/" | relative_url }}), en orden de declaración. Es lo que llaman implícitamente los string templates (`"$user"`), `println` y casi todo el logging.

```kotlin
// Not found in FAS — standalone example
data class User(val id: Int, val name: String) { var lastSeen: Long = 0 }

println(User(7, "Ada"))     // User(id=7, name=Ada)  — lastSeen NO aparece

class Plain(val id: Int)
println(Plain(7))           // Plain@6d06d69c
```

## The Senior Nuance (El Matiz Senior)

- **El beneficio para debuggear es la razón principal para usar una data class en un modelo.** Un reporte de crash o una línea de log con `RecurrenceRule(frequency=WEEKLY, interval=2, ...)` le gana a `RecurrenceRule@3f2a` por muchísimo.
- **La misma regla de exclusión que [`equals`]({{ "/es/glosario/equals/" | relative_url }}).** Las propiedades declaradas en el cuerpo no aparecen. Si un campo importa para debuggear, va en el constructor primario — o sobreescribís `toString` a mano.
- **Nunca loguees una data class con secretos.** El `toString` generado imprime tokens, contraseñas y emails tal cual; sobreescribilo para esos tipos, o dejá los campos sensibles fuera del constructor.
