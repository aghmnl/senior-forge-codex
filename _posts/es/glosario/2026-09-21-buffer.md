## The Theory (El Qué)

**`buffer(capacity)`** es el operador de [`Flow`]({{ "/es/glosario/flow/" | relative_url }}) que desacopla al productor del colector: las emisiones [upstream]({{ "/es/glosario/upstream/" | relative_url }}) van a un channel y el productor sigue trabajando mientras el colector [downstream]({{ "/es/glosario/downstream/" | relative_url }}) procesa valores anteriores. Sin él, [`emit`]({{ "/es/glosario/emit/" | relative_url }}) suspende hasta que el colector termina. `flowOn` implica un buffer — cruzar un límite de dispatcher necesita un channel de todos modos — y por eso [withContext vs flowOn]({{ "/es/02-coroutines-flow/with-context-vs-flow-on/" | relative_url }}) no es solo un cambio de thread sino también un cambio de concurrencia.

```kotlin
// Not found in FAS — standalone example
// Sin buffer: tiempo total ≈ suma de los tiempos de productor y colector
pages().collect { render(it) }

// Con buffer: productor y colector se solapan
pages().buffer().collect { render(it) }

// flowOn ya bufferea: no hace falta un buffer() extra para el salto en sí
pages().flowOn(Dispatchers.IO).collect { render(it) }
```

## The Senior Nuance (El Matiz Senior)

- **Bufferear cambia memoria y frescura por throughput.** Un buffer sin límite delante de un colector lento crece sin freno; `conflate()` (quedarse solo con el último) suele ser lo correcto para estado de UI.
- **`flowOn` bufferea lo quieras o no.** Agregar `flowOn` a una cadena puede cambiar el timing y el orden observado en los tests aunque el dispatcher sea irrelevante — una sorpresa habitual.
- **Los operadores adyacentes se fusionan.** Un `buffer()` pegado a un `flowOn` u otro `buffer` es fusionado por el runtime en un solo channel con la capacidad más amplia, así que apilarlos no es acumulativo.
