## The Theory (El Qué)

**`delay(millis)`** suspende la [coroutine]({{ "/es/glosario/coroutines/" | relative_url }}) actual por un tiempo dado *sin bloquear* su [thread]({{ "/es/glosario/thread/" | relative_url }}): el dispatcher queda libre para correr otro trabajo y reanuda la coroutine cuando pasa el tiempo. Esa es la diferencia con `Thread.sleep`, que estaciona al thread mismo. `delay` es un [suspension point]({{ "/es/glosario/suspension-point/" | relative_url }}) [cancelable]({{ "/es/glosario/cooperative-cancellation/" | relative_url }}) — lanza [`CancellationException`]({{ "/es/glosario/cancellation-exception/" | relative_url }}) si el job se cancela mientras espera.

```kotlin
// Not found in FAS — standalone example
suspend fun retry(times: Int, block: suspend () -> Unit) {
    repeat(times) { attempt ->
        runCatching { block() }.onSuccess { return }
        delay(1000L * (attempt + 1))   // backoff: suspende, nunca bloquea
    }
}
```

## The Senior Nuance (El Matiz Senior)

- **En los tests, `delay` es tiempo virtual.** Bajo [`runTest`]({{ "/es/glosario/run-test/" | relative_url }}) el [`TestDispatcher`]({{ "/es/glosario/test-dispatcher/" | relative_url }}) lo saltea al instante, así que un backoff de una hora cuesta microsegundos. Por eso un `delay` real en un test está bien y un `Thread.sleep` es un bug.
- **Nunca uses `delay` para "esperar" a otra coroutine.** Hace los tests inestables y el código propenso a races; usá `join()`, `await()` o `advanceUntilIdle()`. Si un test solo pasa con un `delay`, está tapando un problema de sincronización — síntoma común después de agregar un [`flowOn`]({{ "/es/glosario/flow-on/" | relative_url }}) y su [buffer]({{ "/es/glosario/buffer/" | relative_url }}).
- **Es un punto de cancelación.** Un loop con `delay` es cooperativo automáticamente; un loop de CPU cerrado sin uno necesita un `ensureActive()` explícito.
