## The Theory (El Qué)

**`internal`** hace una declaración visible en todo el **mismo módulo** — un módulo de Gradle, en un proyecto Android — e invisible afuera. Se ubica entre [`private`]({{ "/es/glosario/private/" | relative_url }}) (archivo o clase) y `public` (todo), y es el modificador que hace real una arquitectura multi-módulo: un módulo `:feature:tasks` puede exponer tres puntos de entrada públicos y dejar el resto internal. Para las [Extension Functions]({{ "/es/01-kotlin-core/extension-functions/" | relative_url }}) suele ser el punto justo.

```kotlin
// Not found in FAS — standalone example
// Visible en todo el módulo :feature:orders, invisible para :app y otras features
internal fun Order.toUiModel(): OrderUiModel = OrderUiModel(id, total.format())

internal class OrderMapper       // detalle de implementación del módulo
```

## The Senior Nuance (El Matiz Senior)

- **Los límites entre módulos solo existen si los marcás.** Sin `internal`, cada helper es API pública y otros módulos lo van a importar, lo que convierte en silencio un proyecto por capas en una bola de barro.
- **Es en tiempo de compilación y por módulo, no por paquete.** Dos módulos de Gradle que declaran cada uno un helper `internal` no chocan; dos paquetes del mismo módulo sí se ven entre sí.
- **Java no lo respeta.** Desde Java la declaración es pública con el nombre mangleado, así que `internal` te protege de llamadores Kotlin, no de los de Java.
