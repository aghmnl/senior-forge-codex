## The Theory (El Qué)

**Upstream** es todo lo que viene *antes* de un punto dado en una cadena de [`Flow`]({{ "/es/glosario/flow/" | relative_url }}): el builder que produce los valores y cada operador declarado más arriba. En `dao.stream().map { }.flowOn(IO).filter { }.collect { }`, el upstream de `flowOn` es `dao.stream()` más el `map`. La palabra importa porque los operadores que cambian el contexto o bufferean — el `flowOn` de [withContext vs flowOn]({{ "/es/02-coroutines-flow/with-context-vs-flow-on/" | relative_url }}), `buffer`, `conflate` — afectan **solo** a su upstream, nunca a lo que viene después.

```kotlin
// Not found in FAS — standalone example
readFilesFlow()            // ── upstream de flowOn
    .map { it.parse() }    // ── upstream de flowOn
    .flowOn(Dispatchers.IO)
    .filter { it.isValid } // ── downstream: corre en el contexto del colector
    .collect { render(it) }
```

## The Senior Nuance (El Matiz Senior)

- **Upstream es una posición, no un tipo.** El mismo operador es upstream de lo que le sigue y [downstream]({{ "/es/glosario/downstream/" | relative_url }}) de lo que lo precede; `flowOn` parte la cadena exactamente donde lo escribís.
- **Las excepciones bajan, los valores bajan, el contexto sube.** Esa inversión es lo más confuso de `flowOn` y la razón por la que `.catch { }` también ve solo las fallas de *su* upstream.
- **Poné `flowOn` lo más cerca posible del productor.** Todo lo que quede entre el productor y el `flowOn` hereda el dispatcher; los operadores que querés en el contexto del colector van después.
