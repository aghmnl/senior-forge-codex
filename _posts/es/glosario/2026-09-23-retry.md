## The Theory (El Qué)

**`retry(n)`** y **`retryWhen { cause, attempt -> }`** son operadores de [upstream]({{ "/es/glosario/upstream/" | relative_url }}) que se resuscriben al [flow]({{ "/es/glosario/flow/" | relative_url }}) cuando falla: el productor vuelve a correr desde el principio, hasta `n` veces o mientras el predicado devuelva `true`. Van *arriba* de un [`catch`]({{ "/es/glosario/catch/" | relative_url }}) en la cadena — primero reintentar, y recién entregarle el control al `catch` cuando se agotaron los intentos. `retryWhen` es el que vale la pena conocer, porque recibe la causa y el número de intento, así que podés hacer backoff y filtrar por tipo de excepción.

```kotlin
// Not found in FAS — standalone example
remoteTasks()
    .retryWhen { cause, attempt ->
        val transitorio = cause is IOException && attempt < 3
        if (transitorio) delay(1000L * (attempt + 1))   // backoff creciente
        transitorio                                     // true = reintentar, false = rendirse
    }
    .catch { emit(emptyList()) }
    .collect { render(it) }
```

## The Senior Nuance (El Matiz Senior)

- **Reintentá solo lo transitorio.** Una `IOException` puede funcionar en un segundo intento; un error de parseo o un 4xx va a fallar idéntico para siempre, y reintentarlo solo quema batería y demora el error que el usuario necesita ver.
- **Siempre con backoff, nunca en loop cerrado.** Un `retry(3)` sin [`delay`]({{ "/es/glosario/delay/" | relative_url }}) golpea el servidor tres veces en microsegundos. Un delay creciente es la diferencia entre un reintento y una denegación de servicio accidental contra tu propio backend.
- **El orden importa: retry arriba, catch abajo.** Un `catch` puesto por encima del `retryWhen` consumiría la falla antes de que el reintento llegue a verla.
