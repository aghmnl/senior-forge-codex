## The Theory (El Qué)

Un **lock** protege un fragmento de código para que **solo un thread pueda ejecutarlo a la vez**. Un thread que quiere entrar mientras otro está adentro tiene que esperar a que el lock se libere. En Kotlin sobre la JVM las formas habituales son el bloque [synchronized]({{ "/es/glosario/synchronized-block/" | relative_url }}) y `ReentrantLock`; en coroutines, `Mutex` cumple el mismo papel pero **suspende** la coroutine en vez de bloquear el [thread]({{ "/es/glosario/thread/" | relative_url }}).

```kotlin
// Not found in FAS — standalone example
private val mutex = Mutex()
private var cache: Map<String, Task> = emptyMap()

suspend fun refresh() {
    mutex.withLock {           // una sola coroutine a la vez acá adentro
        cache = api.fetchTasks().associateBy { it.id }
    }
}
```

## The Senior Nuance (El Matiz Senior)

- **Un lock hace esperar a los demás; compare-and-set hace reintentar al que pierde.** [update {}]({{ "/es/glosario/update/" | relative_url }}) no usa lock: nadie espera, y el que pierde la carrera recalcula. Por eso es barato para cambios de estado chicos y rápidos.
- **Nunca bloquees un thread adentro de una coroutine.** Un bloque `synchronized` que espera bloquea el thread entero, incluido el [main thread]({{ "/es/glosario/main-thread/" | relative_url }}) si corre ahí. En coroutines se usa `Mutex`, que suspende.
- **Los locks pueden trabarse (deadlock).** Dos fragmentos de código que tienen cada uno un lock y esperan el lock del otro esperan para siempre. Mantener corta la sección protegida, y no llamar código desconocido adentro, evita la mayoría de los casos.
